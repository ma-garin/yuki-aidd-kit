# 診断の書式（`docs/odc_analysis.md`）

`verify-agent`（ループ4）と `e2e-cycle` ステップ4 が、修整の前に必ずここへ書く。
狙い: 「直したら通った」という結果論を無くし、直す前に原因を特定したことを跡に残す。
書かずに直した修整は `gate-agent` が差し戻す。

## 項目（この順で書く）

1. **再現手順**: 何を実行すれば起きるか（コマンド・入力・前提状態）。他人がそのまま実行して再現できる粒度で書く
2. **失敗シグネチャ**: エラーメッセージ・スタックトレース・アサーション差分の該当箇所をそのまま引用する（要約しない）
3. **仮説1〜3と根拠**: 原因の仮説を3つまで挙げ、各仮説について「この失敗シグネチャと矛盾しない理由」を書く。当てずっぽうの列挙ではなく、シグネチャから逆算する
4. **最小再現で1つに絞る**: 仮説ごとに最小の再現手順（ケースを削る・入力を単純化する等)を試し、成立する/しない結果で仮説を1つに絞る。絞れない場合はその旨と理由を書き、修整に進まない
5. **原因箇所**: 絞った仮説が指す実装またはテストの `file:line`

## 記入例

```
1. 再現手順: `npx playwright test -g "在庫0件で購入不可"` を単独実行すると FAIL する。並列実行時のみ再現し、単独直列実行では再現しない
2. 失敗シグネチャ: `expect(locator).toBeDisabled()` タイムアウト。実測は enabled のまま
3. 仮説:
   - a) 別テストが同じ在庫データを先に書き換えている（共有状態） — 並列時のみ再現する事実と整合する
   - b) locator が別要素に当たっている（locator 破損） — 単独実行でも再現するはずなので、単独直列で再現しない事実と矛盾する
   - c) ボタンの disabled 化がタイミング依存（flaky） — 単独直列で常に PASS する事実と矛盾する（flaky なら単独でも時々落ちるはず）
4. 最小再現: 対象テストだけを `--workers=1` で5回反復 → 全て PASS。他テストと同時実行時のみ FAIL → 仮説 a) に絞る
5. 原因箇所: `tests/fixtures/inventory.ts:42`（テスト間で在庫テーブルを共有し、後始末していない）
```

## 分類とテスト陳腐化・環境依存・flaky の判定

「製品欠陥 / テスト陳腐化（locator 破損／仕様変更）/ 環境・データ依存 / flaky」の分類とその判定手順は
`skills/e2e-cycle/references/failure-rules.md`（ステップ4）を見る。診断はその分類の**前**に行う下ごしらえで、
分類自体は診断で絞った原因箇所をもとに行う。

## 修整の限定

- 修整は「観測した失敗を狙った最小差分」に限る。診断で特定していない箇所を「ついでに」直さない
- 直す前に、その欠陥を再現するテストが赤であることを確認する（診断の手順4で既に確認済みのはず）
- 修整後は再現テストと既存回帰を別々に実行し、`git apply -R <patch>` で修整差分だけを逆適用して赤に戻ることを確認する（`git stash`/`checkout`/`reset` は使わない。H-2）
- 乖離点（診断で立てた前提と、逆適用で確かめた実際の挙動の差）を示せない修整は差し戻す
