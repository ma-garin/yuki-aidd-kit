# 工程承認レビュー（人間が判子を押す前に指摘を出し切る）

AIDD の手戻りは「成果物が全部出てきてから誤りが見つかる」ときに最大になる。
要件の取り違えが基本設計に入り込めば、詳細設計・実装・単体〜システムテストまで全部その上に積まれる。
本スキルは**各工程の出口で誤りを1工程分に閉じ込める**ためのレビューを回す。

## 越えない線

| AI がやること | AI がやらないこと |
|---|---|
| 出口基準に対して指摘を出し切る | **承認する**（`approver` 欄を埋める） |
| 根拠（確認した対象・件数）を書く | 合否の最終判断 |
| 差し戻し事項に ID と解消の検証方法を付ける | 「その設計が本当にその要件を満たすか」の判断 |

**AI が承認すると第三者検証としての価値が消える。** 出力は人間への**申し送り**であり、判定欄は人間が埋める。
機械が判定できる範囲は `./scripts/check-approval.sh`（承認記録の有無・版の一致・矛盾の検出）まで。

## 3 役を順次で回す（並列にしない）

Agent への並列委譲はトークンが**約 7 倍**になり、Pro＋Sonnet では上限に当たる（`rules/model-routing.md`）。
**同一セッションで 1 役ずつ、前の役の出力を読んでから次へ進む。** 重複した指摘は後の役が引き継がず削る。

| 順 | 役 | 読むもの（これ以外を読まない） | 出す指摘 |
|---|---|---|---|
| 1 | **追跡担当** | `traceability-matrix.md` ＋ `./scripts/trace-check.sh docs/lifecycle` の出力 | 上流 ID で下流に紐づいていないもの、空欄、孤立したテスト。**ID で列挙する** |
| 2 | **仕様一致担当** | **上流工程の成果物と当該工程の成果物だけ**（実装コードを読まない） | 上流の項目が当該工程で落ちている／意味が変わっている／上流に無いものが増えている（スコープ膨張） |
| 3 | **リスク担当** | 当該工程の成果物 ＋ `skills/qa-review-standards`（テスト工程 5〜8 は `./scripts/test-metrics.sh` の検知も） | 異常系・境界値・非機能の抜け。ISTQB severity を付ける。テスト工程では unread・Critical/High 残・滞留・偏りを差し戻し事項に |

役2が実装コードを読むと「実装の写し」になり、設計と実装の食い違いを検出できなくなる（`dev-lifecycle` の
「前工程の成果物だけを入力にする」と同じ理由）。

## 手順

1. `./scripts/check-approval.sh --phase <n>` を実行し、現在の状態を確認する
2. 判定基準を `skills/dev-lifecycle/references/phase-gates.md` 第 n 工程の出口基準から引く（**ここに基準を複製しない**）
3. 役1 → 役2 → 役3 の順に実施し、各役の結果を `docs/lifecycle/approvals/phase-<n>-ai.md` へ**追記**する（上書きしない）
4. 人間へ渡す: 「差し戻し事項 N 件。承認欄は空のままです」と明示して終了する
5. 人間が指摘を潰したら、**差し戻した役だけ**が再レビューする（全役をやり直さない）
6. **最大 2 ラウンド。** 2 周で収束しなければ人間へエスカレーションする
   （`phase-gates.md`「差し戻しが3回続いた工程は粒度が合っていない兆候」）

## 出力形式（`phase-<n>-ai.md` に追記する）

```markdown
## ラウンド <r> / 役 <1|2|3> <役名> — <YYYY-MM-DDTHH:MM:SS+09:00>

申し送り判定: 承認可 / 条件付き承認可 / 差し戻し推奨
（**これは承認ではない。** 人間が phase-<n>.md で判定する）

### 根拠

| 出口基準 | 確認した対象（ファイル・ID・件数） | 結果 |
|---|---|---|

### 差し戻し事項

| ID | 内容 | 解消の検証方法 | severity |
|---|---|---|---|
| R-<n>-1 |  |  | Critical / High / Medium / Low |

### 未確認事項（unknown）

- <判定できなかった項目。ここを空欄にして「承認可」と書かない>
```

- ID は `R-<工程番号>-<連番>`。ラウンドをまたいで通し番号にする
- **「解消の検証方法」が書けない指摘は差し戻さない。** 受け手が完了を判定できない指摘は指摘として不十分
- 根拠は evidence-only。「確認した」だけは根拠ではない。**確認したファイル・ID・件数を書く**
- 判定できなかった項目は unknown に残す。**判定不能を合格に数えない**

## 人間が承認するとき（AI は代行しない）

1. `phase-<n>-ai.md` の差し戻し事項が全て解消されていることを確認する
2. `docs/lifecycle/approvals/phase-<n>.md` の判定・根拠・`approver`・`approved_at` を埋める
3. `./scripts/phase-hash.py <covers のパス>` の出力を `reviewed_hash` に貼る
4. `./scripts/check-approval.sh --phase <n>` が exit 0 になることを確認する

**承認後に成果物を変更すると承認は自動失効する。** 変更したら承認を取り直す。
