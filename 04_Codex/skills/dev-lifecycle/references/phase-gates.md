# 工程ゲート（入口/出口基準）

各工程の開始条件（入口）と完了条件（出口）。`dev-lifecycle` スキルから参照する詳細層。
出口基準を1つでも満たさない工程は「完了」と判定しない。共通4項目（TBD 残ゼロ／`trace-check.sh` NG=0／
自己レビュー Critical・High 残ゼロ／**承認記録があり `check-approval.sh --phase <n>` が exit 0**）は全工程に加えて適用する。

## 承認ゲート（全工程共通）

各工程の出口には**人間の承認**を置く。承認は記録に残し、**承認した時点の成果物の版に縛る**
（`docs/lifecycle/approvals/phase-<n>.md` の `reviewed_hash`）。
承認後に成果物が変われば承認は自動失効する。これが無い承認は、判子を押した後に中身が差し替わるのと同じで形骸化する。

| 機械が判定する（`./scripts/check-approval.sh`） | 人間しか判定できない |
|---|---|
| 承認記録が存在するか・必須欄が埋まっているか | その設計が**本当にその要件を満たすか** |
| 承認時の版と現在の版が一致するか（失効検出） | 受入基準の解釈が依頼者の意図と合っているか |
| 未解消の差し戻し事項・未確認事項を残したまま「承認」になっていないか | 残存リスクを受容してよいか |
| `approver` が人間か | 条件付き承認の条件が妥当か |
| 着手済み工程の直前の着手済み工程が承認されているか（工程順序） | |

この線を曖昧にすると「AI が承認した」ことになり、第三者検証としての価値が消える。
AI は `/phase-review <n>`（`skills/phase-approval`）で**指摘を出し切るところまで**を担う。

- 判定は3値: `承認` / `条件付き承認` / `差し戻し`。未記入は判定値ではなく「未承認」という状態
- 差し戻し事項には ID と**解消の検証方法**を必須にする。書けない指摘は差し戻さない
- 運用の詳細は `02_共通/ひな形/lifecycle/approvals/README.md`
- 強制したい場合: プロジェクトルートに `.claude/phase-gate` を置くと、`block-phase.py` hook が
  **前工程が未承認のまま次工程の成果物を書くこと**を物理的にブロックする（バイパス用の環境変数は無い）

## 0. RFD（Request for Discussion）

- **入口**: 解きたい課題または要望が1文で言える
- **出口**:
  - [ ] 課題・背景・影響範囲が書かれている
  - [ ] 選択肢が2つ以上あり、それぞれの利点・欠点・コストが並記されている
  - [ ] 決定と却下理由が書かれている（**人間の承認が必須**）
  - [ ] スコープ外を明示している
  - [ ] 決定は ADR（`02_共通/ひな形/ADR-template.md`）へ転記する

## 1. 要件定義

- **入口**: RFD の決定が承認済み
- **出口**:
  - [ ] 全 `REQ-F` に**観測可能な受入基準**がある（「使いやすいこと」は不可、「操作3回以内で完了する」は可）
  - [ ] 全 `REQ-N` が ISO/IEC 25010 の特性で分類され、既定値は `nfr-standards` から引いている
  - [ ] 各要件に優先度（MoSCoW: Must/Should/Could/Won't）が付いている
  - [ ] 対象外（Won't）が明記され、AI の探索範囲を制限している
  - [ ] 前提・制約・依存（外部 API・無料枠・端末）が列挙されている
  - [ ] 全要件が `RFD-xxx` に紐づく（紐づかない要件はスコープ膨張として差し戻す）
  - [ ] **人間の承認が必須**

## 2. 基本設計（外部設計）

- **入口**: 要件定義が承認済み
- **出口**:
  - [ ] 全 `REQ-F` が1つ以上の `BD-xxx` に割り当てられている（未割り当てゼロ）
  - [ ] 構成要素（画面・モジュール・外部 I/F・データストア）が列挙され、責務が1行で書かれている
  - [ ] 画面/UI がある場合、`design-system` のトークンを参照している（値の再定義をしない）
  - [ ] データモデル（スキーマ・キー・バージョン）が定義されている
  - [ ] 外部 I/F の入出力・エラー時の挙動が定義されている
  - [ ] 主要な技術選定に理由（比較表）がある。判断が重い場合は ADR を起こす
  - [ ] `REQ-N` の実現方式が書かれている（性能・オフライン・セキュリティをどう満たすか）

## 3. 詳細設計（内部設計）

- **入口**: 基本設計が確定
- **出口**:
  - [ ] 全 `BD-xxx` が1つ以上の `DD-xxx` に分解されている
  - [ ] 各 `DD` に、対象ファイル・関数/クラス・入出力・事前条件・事後条件がある
  - [ ] **異常系**（入力不正・通信失敗・容量超過・権限なし）の扱いが定義されている
  - [ ] 境界値（最大長・0件・上限件数・日付境界）が明示され、UT の入力に使える
  - [ ] 状態を持つ場合、状態遷移が表または図で書かれている
  - [ ] 実装者が追加調査なしで書ける粒度である（実装モードで再探索が不要）

## 4. 実装

- **入口**: 詳細設計が確定し、`PLAN.md` が作られている
- **出口**:
  - [ ] 全 `T-xxx` が完了し、対象 `DD-xxx` を明記している
  - [ ] 1コミット＝1論理変更、Conventional Commits に従っている
  - [ ] 秘密情報が混入していない（`scripts/pre-commit` またはリポジトリの secret scan が通る）
  - [ ] 設計から逸脱した箇所は `04-implementation.md` に理由付きで記録し、設計書へ逆同期している
  - [ ] `implement-profile` の規範（再探索しない・plan 準拠）に従った

## 5. 単体テスト（UT）

- **入口**: 対象 `DD` の実装が完了
- **出口**:
  - [ ] 全 `DD-xxx` に1つ以上の `UT-xxx` がある
  - [ ] 正常系・異常系・境界値の3区分がそれぞれ存在する
  - [ ] テストは実装と独立に書かれている（実装に合わせて期待値を緩めていない）
  - [ ] 外部依存（LLM・ネットワーク・時刻）はモック化されている
  - [ ] 実行結果（pass/fail 件数）を evidence として提示できる

## 6. 結合テスト（IT）

- **入口**: 関連する UT が全て pass
- **出口**:
  - [ ] 全 `BD-xxx` の I/F に1つ以上の `IT-xxx` がある
  - [ ] モジュール間のデータ受け渡し（型・必須項目・文字コード）を検証している
  - [ ] 外部 I/F の失敗時（タイムアウト・4xx/5xx・不正レスポンス）の挙動を検証している
  - [ ] データのライフサイクル（作成→更新→削除→復元）を追跡している（FedEx Tour）

## 7. システムテスト（ST）

- **入口**: 結合テストが全て pass し、本番相当の構成で動作する
- **出口**:
  - [ ] 全 `REQ-N` に1つ以上の `ST-xxx` があり、**実測値**が記録されている（「速い」ではなく「初期表示 2.1 秒」）
  - [ ] 対象端末幅・ブラウザで主要シナリオが通る（既定値は `nfr-standards`）
  - [ ] オフライン/障害時の挙動を検証している（該当する場合）
  - [ ] セキュリティ観点（秘密情報の露出・XSS・越境データ）を検証している
  - [ ] 検出した欠陥に `DEF-xxx` と ISTQB severity が付いている

## 8. 受け入れテスト（UAT）

- **入口**: システムテストの Critical/High 欠陥が残ゼロ
- **出口**:
  - [ ] 全 `REQ-F` の受入基準に対して `UAT-xxx` が1対1以上で存在する
  - [ ] 実際の利用シナリオ（業務の流れ）で通しで実行している
  - [ ] 合否とその根拠（画面・ログ・出力ファイル）が記録されている
  - [ ] 不合格項目の扱い（修正 / 次リリース / 受容）が決まっている
  - [ ] **人間の承認が必須**（AI は合格判定をしない）

## 9. 保守運用

- **入口**: UAT 合格
- **出口**:
  - [ ] 稼働環境・依存・復旧手順が `09-operations.md` に書かれている
  - [ ] 監視項目と異常の判断基準（しきい値）が定義されている
  - [ ] 変更手順（リリース・ロールバック）が書かれ、1度は実行して確認している
  - [ ] 既知の制約・技術的負債が一覧化されている
  - [ ] 引き継ぎ時に読む順序（`CURRENT_STATE.md` → 追跡表 → 運用手順）が明記されている
  - [ ] `retro` を実施し `lessons.md` へ反映済み

## 差し戻しの規則

- 出口基準の未達は**次工程の作業で埋めない**。必ず当該工程へ戻す
- 要件の追加・変更は RFD へ戻す（実装中に要件を足さない）
- 差し戻しが3回続いた工程は、粒度が合っていない兆候。工程を分割するか、軽量 SDD へ切り替える判断を人間に求める
