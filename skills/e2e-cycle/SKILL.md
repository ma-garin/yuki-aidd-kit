# 汎用AIエージェント型E2Eテスト＆不具合修整ワークフロー

出所: 個人運用の `~/.claude/skills/e2e-cycle`（2026-08）。テスト戦略全体は `skills/test-strategy`、テストケース CSV の列は `templates/test/system_test_cases.csv`（ツアー観点・severity 付き）に合わせる。

テスト設計から不具合修整・コミットまでを5フェーズに分割して実行する。
**1回の起動で1フェーズだけ実行し、完了したら必ず停止してユーザーの指示を待つ。**

## 絶対原則（全フェーズ共通・例外なし）

1. **1サイクル1停止**: 1つの起動で複数フェーズを連続実行しない。指定フェーズが完了したら「ステップN完了」と報告し、次フェーズへ自動で進まずプロセスを終了する。
2. **待機・監視の完全禁止**: `sleep`、ポーリング（定期的な状態確認・ログの再帰的監視）、バックグラウンド実行（コマンド末尾の `&` 等）を一切使わない。
3. **実行と状態管理の分離**: テストの終了を「監視」しない。コマンドはフォアグラウンド（同期処理）で1回だけ発行し、標準出力が返るまでターミナルをブロックして待つ。

## フェーズの決定

- 引数にフェーズ番号（1〜5）があれば、そのフェーズだけを実行する。
- 引数がない場合は成果物の有無で次フェーズを判定し、判定結果を1行で宣言してからその1フェーズだけを実行する。

| 状態 | 実行フェーズ |
|---|---|
| テストケースCSVが無い | 1 |
| CSVはあるがE2Eテストスクリプトが無い | 2 |
| スクリプトはあるが結果JSONが無い | 3 |
| 結果JSONにFailが残っている | 4 |
| 全Pass（または残Failをユーザーが許容済み） | 5 |

## 成果物の既定パス

プロジェクトに既存の規約・ディレクトリ構成があればそちらを優先する。

- テストケースCSV: `docs/system_test_cases.csv`
- Playwright設定: `playwright.config.ts`（Pythonプロジェクトでは pytest-playwright 相当に読み替える）
- スクリーンショット・動画: `e2e/artifacts/`
- テスト結果JSON: `e2e/results/results.json`
- ODC分析レポート: `docs/odc_analysis.md`

## ステップ1: テスト設計とテストケース作成（計画フェーズ）

**目的**: 本システムのユーザー価値とUI/UXの向上を目的としたシステムテストの計画と、テストケースの作成。AIエージェントの自律ループによるトークン消費を防ぐため、以下の指示をすべて実行した後は、いかなる待機や監視も行わず、直ちにプロセスを完了・停止する。

1. プロジェクトのディレクトリをスキャンし、システムの全体像とUIコンポーネントの構造を把握する（コードの変更はまだ行わない）。
2. システムが提供するユーザー価値を最大化する観点で、ユースケースをロール別・ペルソナ別にMECE（漏れなくダブりなく）に洗い出す。
3. テストケースを作成し、CSV形式（列: テストID, ロール, 対象機能, ツアー観点, テスト目的, 前提条件, 手順, 期待される結果, severity。雛形 `templates/test/system_test_cases.csv`）でファイル（`docs/system_test_cases.csv` 等）に出力する。
4. CSVファイルの出力が完了したら、絶対にテストの実行や次のステップへの移行は行わず、「ステップ1完了」と報告してプロセスを終了する。

## ステップ2: Playwrightテストスクリプトの生成（準備フェーズ）

**目的**: ステップ1で作成したテストケース（CSV）を自動化するため、Playwrightを用いたE2Eテストスクリプトを作成する。自律ループによるトークン消費を防ぐため、完了次第、実行はせずにプロセスを停止する。

1. ステップ1で出力したテストケースのCSVファイルを読み込む。
2. CSVの内容を網羅するPlaywrightのテストスクリプトおよび設定ファイル（`playwright.config.ts`）を作成・更新する。
3. 以下の要件を必ず実装・設定に含める:
   - ロール別・機能別のテストケースを並列実行できる構造にすること。
   - テスト実行時に画面のスクリーンショットおよび動画（`video: 'on'`, `screenshot: 'on'`）を自動取得し、指定ディレクトリ（`e2e/artifacts/` 等）に保存すること。
   - テスト結果とエラー詳細をJSON形式で出力するレポーター設定（`outputFile: 'e2e/results/results.json'` 等）を含めること。
4. スクリプトファイルおよび設定ファイルの作成が完了したら、絶対にスクリプトを実行せずに、「ステップ2完了」と報告してプロセスを完全に終了する。

## ステップ3: 安全なテスト実行（実行フェーズ）

**目的**: 作成したPlaywrightのテストスクリプトを実行し、テスト結果を取得する。トークンの大量消費（ループ暴走）を完全に防ぐため、以下のルールを厳格に遵守する。

1. コマンド（例: `npx playwright test`）を使用してテストを実行する。
2. 【絶対遵守ルール: 暴走防止】テストの実行において、`sleep` コマンドの使用、ポーリング（定期的な状態確認やログの再帰的監視）、およびバックグラウンド実行（コマンド末尾の `&` など）を一切禁止する。
3. 実行コマンドはフォアグラウンド（同期処理）で1回のみ発行し、ターミナルの標準出力をそのまま待機する。自律的なステータスチェックループは回さない。
4. テスト実行が完了（またはタイムアウトで終了）したら、生成されたJSON結果ファイル等の存在を確認し、Pass/Fail/Skipの件数概要のみを簡潔に報告する。
5. 報告が完了したら、不具合の分析や修整には自動で進まず、「ステップ3完了」と宣言してプロセスを完全に停止し、ユーザーの次の指示を待つ。

## ステップ4: ODC分析・段階的修整・再テスト（修整検証サイクル）

**目的**: テスト実行結果（JSONログ等）を読み込み、不具合のODC分析、ソースコードの修整、および再実行による検証を行う。自律ループによる暴走を防ぐため、以下のステップと停止条件を厳格に守る。

1. 出力されたPlaywrightのテスト実行結果（JSONログ）を読み込む。
2. NGとなったテスト（不具合）について、ODC（Orthogonal Defect Classification）を用いて分類・分析し、レポートを出力する。併せて「製品欠陥 / テスト陳腐化 / 環境・データ依存 / flaky」を判定し、テストと実装のどちらを直すかを `templates/test/iso29119-incident-report.md` の形式で記録する。機能の正常性だけでなく、ユーザー価値やUI/UXの観点（アクセシビリティや使いやすさ）の評価も必ず含める。
3. 分析結果に基づき、致命的な不具合やUI/UXを著しく損なっている箇所から順にソースコード（またはテスト資産）を修整する。
4. 【絶対遵守ルール: 修整と再テストの反復】一度にすべての不具合を直そうとしない。1〜2個の主要な不具合（または関連コンポーネント）の修整が完了するごとに、以下の検証手順を実行する:
   a. 対象のテストケースのみを対象とした再テスト（例: `npx playwright test -g "対象テスト名"`）を、フォアグラウンド（同期処理）で1回だけ実行する。`sleep` やポーリングは一切禁止。
   b. 再実行結果のログと、Playwrightが取得したスクリーンショットや動画の出力状況を確認し、修整がUI/UXの観点も含めて正しく反映されているか検証評価を行う。
5. 上記4の1サイクルの検証評価が終わったら、次の不具合修整には自動で進まず、変更内容と検証結果を報告した上で「修整確認待ち」としてプロセスを完全に停止する。

※残りの不具合が解消するまで、ユーザーがステップ4を繰り返し起動する（サイクル2、サイクル3…）。1起動＝1サイクル（不具合1〜2個）とする。

## ステップ5: ドキュメント同期と最終Gitコミット（完了フェーズ）

**目的**: 今回のシステムテスト・ODC分析・アプリ修整・テスト資産更新およびドキュメント整備の成果物をGitへコミットする。

1. `git status` を確認し、今回作成・変更されたファイル（アプリコード、E2Eテストコード、CSV、ドキュメント類）をパス明示で `git add` する（`git add -A` は使わない）。動画やスクリプト実行ログ（`artifacts/` や `results/` などのバイナリ・一時ログ）が `.gitignore` に含まれており、コミット対象外になっていることを確認する。
2. 適切なコミットメッセージ（例: `test: PlaywrightによるE2Eシステムテスト構築、不具合修整およびドキュメント更新`）を作成し、コミットを実行する。push はユーザーの指示範囲に含まれる場合のみ行う。
3. コミット完了後、ステータスを報告して終了する。
