# トレーサビリティ ID 体系と追跡表

`dev-lifecycle` の中核。要件が設計・実装・テストのどこに落ちたかを**機械検証可能**にするための規約。
検証は目視でなく `./scripts/trace-check.sh [対象ディレクトリ]` で行う（`context-compression` 原則3: 決定論的作業はスクリプト化）。

## ID の書式

```
<接頭辞>-<3桁の連番>        例: REQ-F-012, DD-003, UAT-007
```

| 接頭辞 | 意味 | 所有ファイル（定義してよい唯一の場所） |
|---|---|---|
| `RFD` | 提案・論点 | `00-rfd.md` |
| `REQ-F` | 機能要件 | `01-requirements.md` |
| `REQ-N` | 非機能要件 | `01-requirements.md` |
| `BD` | 基本設計要素 | `02-basic-design.md` |
| `DD` | 詳細設計要素 | `03-detailed-design.md` |
| `T` | 実装タスク | `04-implementation.md`（SDD の `tasks.md` と同じ番号を使う） |
| `UT` | 単体テストケース | `05-unit-test.md` |
| `IT` | 結合テストケース | `06-integration-test.md` |
| `ST` | システムテストケース | `07-system-test.md` |
| `UAT` | 受け入れテストケース | `08-acceptance-test.md` |
| `OPS` | 運用手順・監視項目 | `09-operations.md` |
| `DEF` | 欠陥 | 検出したテスト工程の文書内 |

## 定義と参照

- **定義**: 所有ファイル内で、①見出し行の先頭（`### REQ-F-001 ...`）または②表の第1セル（`| REQ-F-001 | ... |`）に書く。この2形式以外は定義とみなさない
- **参照**: 他の工程文書からは本文中に ID を書くだけでよい。**再定義しない**（同じ ID を別ファイルの見出し/第1セルに書かない）
- 連番は詰めない。削除した ID は欠番のまま残す（過去の参照を壊さないため）
- 1つの ID に複数の内容を詰めない。「AかつB」は2つに分ける（テストが1対1で書けなくなるため）

## 追跡表（`traceability-matrix.md`）

要件と下流成果物の対応は**この表だけ**が真実源。各工程文書に対応表を複製しない。

| REQ-ID | 要件（要約） | 由来 RFD | BD | DD | 実装 T | UT | IT | ST | UAT | 状態 |
|---|---|---|---|---|---|---|---|---|---|---|
| REQ-F-001 | ... | RFD-001 | BD-001 | DD-001, DD-002 | T-003 | UT-005 | IT-002 | — | UAT-001 | 合格 |

- 1セルに複数 ID を書く場合はカンマ区切り
- 該当しないセルは `—`（全角ダッシュ）または `-` を入れる。**空欄はカバー漏れとして検出される**
- `REQ-F` は UAT 列必須、`REQ-N` は ST 列必須（V字の対応）
- 状態: `未着手 / 実装中 / 検証中 / 合格 / 保留`

## `trace-check.sh` が検出するもの

| 検査 | 内容 | 典型的な原因 |
|---|---|---|
| 重複定義 | 同じ ID が複数箇所で定義されている | コピペで工程文書に対応表を複製した |
| 未定義参照 | 参照されているが所有ファイルに定義がない | 設計で存在しない要件を実装した／採番ミス |
| 追跡表に未記載 | 定義済みの `REQ-*` が追跡表にない | 要件追加時に表を更新していない |
| カバー漏れ | 追跡表の必須セル（BD/DD/UAT または ST）が空 | 設計・テスト未着手のまま次工程に進んだ |
| 孤立テスト | `UT/IT/ST/UAT` が追跡表から参照されていない | 要件と無関係なテストを書いた／表の更新漏れ |

出力は「結論（NG 件数）→ 根拠（種別ごとの件数）→ 詳細（ファイルへ書き出し）」の3層。会話には結論と根拠だけを出す。

## 欠陥（`DEF`）の扱い

- 発見したテスト工程の文書内に定義し、`{DEF-ID, 対象 REQ/DD, severity, evidence, 再現手順, 対応}` を記録する（形式は `qa-review-standards` に従う）
- severity は ISTQB の Critical / High / Medium / Low。severity と priority を混同しない
- Critical/High は当該工程の出口基準（残ゼロ）に直結する。Medium/Low は `09-operations.md` の既知の制約へ引き継ぐ

## GitHub との接続

- Issue タイトルの先頭に ID を置く（例: `[REQ-F-012] エクスポート形式に CSV を追加`）
- PR 本文に `REQ-F-012 / DD-003 / UT-005` のように関係 ID を列挙する。`templates/github/pull_request_template.md` がこの欄を持つ
- CI で `trace-check.sh` を回す（`github-actions/lifecycle-check.yml`）。追跡漏れをレビュー前に落とす
