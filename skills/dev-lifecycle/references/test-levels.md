# テストレベル別の設計観点（UT / IT / ST / UAT）

`dev-lifecycle` の詳細層。**同じ観点を複数レベルで重複して書かない**ための分担表。
テストコードの生成・実行方法は `skills/test-automation`、レビュー規格（severity・ツアー）は `skills/qa-review-standards`、非機能の既定値は `skills/nfr-standards` が真実源。ここには重複させない。

## 分担の原則

| レベル | 何を疑うか | 検証対象の ID | 落としてはいけないもの |
|---|---|---|---|
| UT | ロジックが仕様どおりか | `DD-xxx` | 分岐・境界・異常入力 |
| IT | つなぐと壊れないか | `BD-xxx` | I/F の型・順序・失敗時 |
| ST | 本番相当で要求を満たすか | `REQ-N-xxx` | 実測値・環境依存 |
| UAT | 依頼者の目的を果たすか | `REQ-F-xxx` | 業務の通し・受入基準 |

下位レベルで潰せる欠陥を上位レベルで見つけるのは手戻りコストが高い。「ST で初めて分岐漏れが出た」は UT の設計不足として `retro` に記録する。

---

## 単体テスト（UT）

### 技法
- **同値分割**: 入力を「有効クラス／無効クラス」に分け、各クラス1件
- **境界値分析**: 境界とその前後（`0 / 1 / max-1 / max / max+1`）
- **分岐網羅**: `DD` に書かれた条件分岐を全て1回は通す
- **デシジョンテーブル**: 条件が3つ以上絡む判定ロジックに適用

### 必須の3区分
1. 正常系（代表値1件）
2. 異常系（`DD` の「異常系」節に書いた全ケース）
3. 境界値（`DD` の「境界値」節に書いた全ケース）

### 規律
- 外部依存（LLM API・ネットワーク・現在時刻・乱数）は必ずモック化。非決定性をテストに持ち込まない
- LLM の**出力品質**は UT で判定しない（`agent-eval` の責務）。UT で見るのは「呼び出し・整形・エラー処理」のロジック
- 実装を見てから期待値を決めない（Verifier 原則）

## 結合テスト（IT）

### 観点
- **I/F 契約**: 引数・戻り値の型、必須項目、null/空配列、文字コード、日付形式
- **順序と状態**: 呼び出し順が変わったとき、前の操作の状態が残るとき
- **外部 I/F の失敗**: タイムアウト、4xx、5xx、レート制限、不正な JSON、部分レスポンス
- **データのライフサイクル**（FedEx Tour）: 作成 → 参照 → 更新 → 削除 → 復元/インポートまで1本の流れで追う
- **永続化**: 保存後のリロードで復元されるか、スキーマ version 変更時にマイグレーションが動くか

### 規律
- モックは「外部サービス境界」まで。自分のモジュール同士はモックせず実物でつなぐ（つないだ時の破綻を見るのが目的）
- 失敗系を必ず含める。正常系だけの IT は IT ではない

## システムテスト（ST）

`REQ-N` に1対1で対応させ、**実測値を必ず記録する**。「速い」「軽い」は不合格の書き方。

### 観点（該当するものだけ実施し、非該当は追跡表で `—`）
- **性能効率性**: 初回ロード時間、主要操作の応答時間、データ件数を増やしたときの劣化
- **互換性/デバイス**: 対象ブラウザ、対象端末幅（既定値は `nfr-standards`）でのレイアウトと操作
- **信頼性**: オフライン動作、通信断からの復帰、異常終了後のデータ保全、export/import の往復
- **セキュリティ**: 秘密情報がコード/ビルド成果物/ログに出ていないか、XSS（`innerHTML` 経路）、越境データ（マルチテナント）
- **使用性/アクセシビリティ**: コントラスト比、キーボード操作、タッチターゲット寸法
- **長時間稼働**（All-Nighter Tour）: 常駐・繰り返し操作でのメモリ・ストレージ増加

### 記録形式
`{ST-ID, 対象 REQ-N, 測定条件, 実測値, 判定基準, 合否, evidence}`。evidence は計測ログ・スクリーンショット・Lighthouse 出力などのパス。

## 受け入れテスト（UAT）

### 観点
- `REQ-F` の**受入基準の文言をそのままテスト手順にする**。基準がテストに書き換えられないなら、要件定義の書き方が悪い（要件定義へ差し戻す）
- 機能単位でなく**業務シナリオ単位**で通す（ログイン → 入力 → 出力 → 共有 のように end-to-end）
- 探索的観点を1周入れる（`qa-review-standards` の Whittaker ツアーから、最低限 Money Tour と Saboteur Tour）
- 実データに近い量・内容で行う（1件だけのテストデータで合格にしない）

### 規律
- **合否判定は人間が行う**。AI は手順の実行・evidence の収集・不一致の報告までを担当する
- 不合格項目は「修正 / 次リリースへ送る / 受容する」のいずれかを明示的に決める。未決のまま完了にしない
- 合格後は `09-operations.md` へ既知の制約を引き継ぐ

---

## AI に実行させるときの注意

- テストケースは**左側の成果物（DD/BD/REQ）だけを入力にして生成する**。実装コードを読ませてから生成すると、実装の写しになり欠陥を検出できない
- 生成後に「どの ID を検証しているか」が全ケースに書かれているか確認する。書けないケースは要件・設計の抜けを示している
- 件数を目標にしない（「50件作って」は水増しを招く）。目標は**カバー漏れゼロ**であり、`trace-check.sh` がその判定を行う
