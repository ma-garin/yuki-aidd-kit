# UI/UXレビュー

## いつ使うか

- 画面を作った・直した後、完了と報告する前
- 「UIをレビューして」と頼まれたとき
- UI/UXの指摘を受けたとき

## なぜ必要か

**画面の問題は、テストが通っていても残る。**

実際に起きたこと（すべて利用者から指摘された）:

- テスト537件・スモーク5件が通っている状態で、結果ページの内容が読めなかった（スクロール不可）
- 部品を作ったが画面に1つも適用せず「対応しました」と報告した
- ステップ1だけを見て「画面を確認した」と報告した（ステップ2/3・モーダルは未確認）
- 同じ画面に単位の違う「件」が3種類あり、検算すると合わなかった

**共通するのは「作った」を「効いている」として報告していること。**
確認の対象が、常に本物より1段浅い。

---

## 手順

### 1. 現物を開く（省略禁止）

**テストの結果だけで完了としない。** Playwright などで実際に開き、上から読む。

「画面を見た」とは、次の**全状態**を見たことを指す。1つでも欠けたら「一部のみ確認」と書く。

| 状態 | 確認すること |
|---|---|
| 通常表示 | ステップがあるなら全ステップ |
| 実行中・読み込み中 | 処理中と分かるか |
| 失敗したとき | 次に何をすればよいか書いてあるか |
| **0件のとき** | 枠だけ残っていないか。読み込み中と区別できるか |
| **狭い画面（縦660px）** | 主要ボタンに手が届くか、スクロールできるか |
| ホバー・フォーカス | 押せる範囲が見た目で分かるか |
| モーダル・対話 | 出したまま閉じられなくなっていないか |

実測すること。**目視で「同じ」と判断しない。**

```js
// 例: ボタンが画面内にあるか
const r = document.querySelector('.btn-primary').getBoundingClientRect();
({ top: r.top, bottom: r.bottom, viewportHeight: window.innerHeight })
```

### 2. 観点で照合する

[references/viewpoints.md](references/viewpoints.md) の74観点を使う。
**照合していない観点は「未検査」と書く。** 全部見たふりをしない。

分類は8つ。優先度「高」から見る。

| 分類 | 何を守るか |
|---|---|
| 操作の到達性 | 押したいものに手が届き、読みたいものが読める |
| 操作の手応え | 操作すると結果が返り、状態が分かる |
| 内容の分かりやすさ | 出ている内容が判断に使える |
| 表示の一貫性 | 同じ役割のものが同じに見える |
| 設定の扱いやすさ | 設定が見つかり、変えられ、保たれる |
| 壊れにくさ | 失敗しても被害が広がらず、気づける |
| 資産の移管性 | 他システムへそのまま渡せる |
| 検証の進め方 | 確かめ方そのものが正しい |

### 3. 部品ではなく画面に適用されているか数える

共通部品を作っただけでは何も変わらない。

```bash
grep -c "Feedback\." target.html     # 0 なら未適用
grep -c "emptyState" target.html
grep -c "confirm(" target.html
```

**呼び出し0件なら「作った」であって「対応した」ではない。**

### 4. 報告する

次がすべて揃っていなければ報告しない。

| 項目 | 悪い例 | 良い例 |
|---|---|---|
| 状態の網羅 | 「画面を確認しました」 | 「ステップ1/2/3・モーダル2種を確認。0件表示は未確認」 |
| 適用の実数 | 「トーストを入れました」 | 「setMessage 20箇所のうち20箇所を置換」 |
| 実測値 | 「横いっぱいになりました」 | 「left=0, width=1440（画面幅と一致）」 |
| 未対応 | （書かない） | 「30項目中17項目が未着手（番号: 3, 7, 9…）」 |

## 直すときの決めごと

### 操作には必ず結果を返す

| 場面 | 出すもの |
|---|---|
| 成功 | トースト（流れて消える） |
| 失敗 | トースト（**消えない**）＋ **次に取るべき行動** |
| 処理中 | ローディング表示 |
| 0件 | 専用の表示。枠だけ残さず、次にできることを書く |
| 危険な操作の前 | 確認。何が起きるかを明記 |

**「エラーが発生しました」だけでは、利用者は止まったままになる。**

### 文言

| 決めごと | 理由 |
|---|---|
| ボタンは動作名にする（「はい／いいえ」「次へ」を使わない） | 押すと何が起きるかがラベルだけで分かる |
| 見出しに動詞を入れない（「〜を決める」） | 何をする場所かは配置で分かる |
| 「（任意）」を付けない | 必須の印が無いことで分かる |
| 実装の説明を書かない（「button の作り」など） | 利用者の判断に使えない |
| 同じ意味の2文目を書かない | 言い換えは情報を増やさない |

変えたら**変更前・変更後・理由**を表にして残す。次に触る人が元へ戻さないため。

### 数字

**同じ画面に単位の違う数字を混ぜない。**

実際にあった例: 同じ「件」で3つの違うものを指していた。

| 数字 | 意味 |
|---|---|
| 37件 | 指摘の種類（同じ内容をまとめた数） |
| 191件 | のべ検出（画面 × 表示幅） |
| 7件 | 1画面内の要素数 |

読み手が検算して合わない数字は出さない。計算に使っていない合計値を並べない。

### 骨格

```
┌─────────────────────────────┐
│ グローバルバー（横いっぱい）    │  製品全体に効くもの
├───────┬─────────────────────┤
│ サイド │ ページヘッダー        │  今どこにいるか
│ ナビ   ├─────────────────────┤
│       │ コンテンツ            │  中身。ここだけスクロール
└───────┴─────────────────────┘
```

- サイドナビは本文と別にスクロールする
- ページヘッダーは1行に収める。パンくず・タイトル・ステップ表示で**同じ語を繰り返さない**
- パンくずの末尾は「今いる段階」。画面内のステップ表示と同じ語を使う
- ナビには**カレント状態**を色・背景・帯の複数で示す（色だけだと見分けにくい人がいる）

### トークン

**直値を書かない。** ある製品では色が105種類・角丸が11種類に増えていた。

| 種類 | 決め |
|---|---|
| 色 | 役割で持つ。強調色は1つに絞る |
| 余白 | 4pxの倍数 |
| 角丸 | 4段階。**内側は外側より小さく** |
| 動き | 0.1〜0.3秒。`prefers-reduced-motion` で止める |
| 本文幅 | 68ch程度。画面幅いっぱいにしない |

### アイコン

意味と形の対応は世の中の慣用に合わせる（設定=歯車、履歴=時計、CLI=ターミナル）。
**外部CDNを読み込まない**（閉じたネットワークで欠ける）。Lucide（ISC）などからSVGを内蔵する。

## やってはいけないこと

| してはいけない | なぜ |
|---|---|
| テストが通ったことを理由に完了と報告する | 画面の問題はテストを通り抜ける |
| 1状態だけ見て「画面を確認した」と言う | 0件・失敗・狭い画面が最も壊れている |
| 部品を作って「対応した」と言う | 適用しなければ何も変わらない |
| 指摘された領域以外の改善を始める | 指摘に応えていないことになる |
| 「良い設計とは」を語る | 利用者が見ているのは画面だけ |

## サーバ起動時の落とし穴

**起動前に使用中のポートを確認する。**

古いプロセスが残っていると、新しいプロセスは EADDRINUSE で静かに落ち、
**古いコードの応答が返り続ける。**画面が旧版のまま見えるため「変更が効いていない」と誤診する。

```bash
lsof -ti:PORT                    # 残っていないか
for pid in $(lsof -ti:PORT); do kill "$pid"; done
```

起動ログが出ていることと、応答サイズが期待どおりかを確認する。
