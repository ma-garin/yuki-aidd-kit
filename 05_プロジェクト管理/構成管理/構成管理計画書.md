# yuki-aidd-kit 構成管理計画書（草案）

準拠: ISO 10007:2017（構成管理の5プロセス＝計画・識別・変更管理・構成の状況記録・構成監査）。
記載項目の粒度は ISO/IEC/IEEE 15289（システム・ソフトウェアライフサイクル情報成果物）を意識し、目的・適用範囲・識別・管理手順・記録・監査の順で構成する。

対象: `/Users/fujimagariyuki/dev/active/yuki-aidd-kit`（個人開発の AIDD Kit）。新構成（案B、00_導入〜06_保守者向け）への移行を前提に、現行運用（Ver.8.0.0、README.md / CHANGELOG.md / INDEX.md / internal/spec/01_構成品目目録.md の記載事実）に基づいて書く。移行未実施の項目は「（移行後）」と注記する。

## 1. 目的・適用範囲

- 目的: キット自身の構成品目を識別し、版・変更・整合性を追跡可能にする（ISO 10007 4.1 の意図に対応）
- 適用範囲: キットの checkout 全体。ただし配布区分（配布／非配布）によって管理の重さを変える（4章）
- 責任者: 保守者 1名（本キットの git 管理者）。承認者もこの保守者を兼ねる

## 2. 構成識別（Configuration Identification）

- 構成品目（CI）の単位: 直下フォルダおよびその1階層下フォルダを基本単位とする。詳細は `構成品目一覧.md`
- 命名規則:
  - 直下フォルダ: 「番号\_日本語名」（例: `01_利用者向け資料`）。番号は導入〜保守の作業順に対応
  - 直下ファイル4点（`README.md` `CHANGELOG.md` `VERSION` `INDEX.md`）は例外的に英語固定名とする。GitHub 等の外部ツールがルート直下でこの名前を前提に扱う（例: README.md はリポジトリ表示、GitHub Actions は `.github/workflows/` 固定）という外部仕様に合わせるため
  - 2階層目以降で外部仕様が名前を強制するもの（`AGENTS.md.template` → Codex が探索する `AGENTS.md`、`CLAUDE.md.template` → Claude Code が読む `CLAUDE.md`、`config.toml`）は英語のまま。それ以外の日本語で成立する名称（ひな形・ツール・学んだこと.md 等）は日本語名にする
- 版識別:
  - キット全体を1つのベースラインとして管理する（サブシステム単位の個別バージョニングはしていない、現行事実）
  - 版の真実源は `VERSION` ファイル。対応する git tag `vX.Y.Z` を打つ（現行 CHANGELOG.md の記載形式を踏襲）
  - 版ごとの変更内容は `CHANGELOG.md` に版が新しい順で記載する（現行運用）

## 3. ベースライン管理

- ベースラインの成立条件: `VERSION` の値を更新し、対応する git tag `vX.Y.Z` を打った時点
- ベースラインの内容確認: `internal/spec/01_構成品目目録.md`（移行後は `06_保守者向け/01_内部仕様/` 配下）に全ファイル目録と実測行数を記録する運用を継続する。現行は「189件・19,901行、2026-09-20 実測」の実測値を保持する方式（推測値を使わない）
- 移行時のベースライン: 案Bへの移行は「互換性のない変更」（現行 Ver.8.0.0 の `agent/` 再編と同種）として扱い、移行完了時点で新しいマイナー/メジャー版を切る。旧パス参照者への影響（外部スクリプトの要更新）を CHANGELOG に明記する現行方式を踏襲する

## 4. 変更管理（Configuration Control）

- 変更経路: PR ベース。mainブランチへの取り込みは保守者が承認する（個人開発のため提案者＝承認者だが、承認の記録は PR のマージ操作そのものとする）
- 変更記録: マージと同じコミットで `CHANGELOG.md` に版・変更理由・互換性影響を記載する（現行運用、Ver.7.1.0/8.0.0 の記載形式）
- 本体変更時の付帯義務（現行運用の事実）: 本体（配布物）を変更したら、同じコミットで `internal/spec/`（移行後 `06_保守者向け/01_内部仕様/`）を更新し、回帰テストと文書整合検査を通す
- 変更区分: 配布物（01〜04相当、現行 `agent/` `docs/` `templates/` `tools/`）の変更は導入先への影響があるため CHANGELOG の互換性注記を必須とする。非配布物（05〜06相当、現行 `project/` `internal/`）の変更は記録のみで可とする

## 5. 構成の状況記録（Configuration Status Accounting）

- 現在版: `VERSION` ファイルの値
- 変更履歴: `CHANGELOG.md`（版ごと、時系列降順）
- 現況棚卸し: `internal/spec/01_構成品目目録.md` を「役割一覧」として保守（移行後 `06_保守者向け/01_内部仕様/`）
- 残課題・次作業: `internal/spec/09_指摘事項.md`（残課題）、`internal/spec/10_バックログ.md`（次にやること）、`project/Roadmap.md`（作業台帳、マイルストーン M番号で管理）。これらは移行後 `05_プロジェクト管理/` `06_保守者向け/` に振り分ける
- 索引: `INDEX.md` が全資産の索引（DAILY/LIBRARY 2層＋タグ＋参照コスト）。エージェント・人間ともここを起点にする現行運用を維持する

## 6. 構成監査（Configuration Audit）

ISO 10007 の機能構成監査（FCA: 要求どおり機能するか）と物理構成監査（PCA: 実体が記録と一致するか）に、現行の自動検査を対応づける。

| 監査区分 | 対応する現行の仕組み | 内容 |
|---|---|---|
| 機能構成監査（FCA） | `ci/test-*.sh`（回帰テスト10本: hooks / install / trace-check / quality-harness / git-gates / check-approval / test-metrics / token-audit / check-docs / check-design） | 各構成品目が仕様どおり動くかを実行して確認する |
| 物理構成監査（PCA） | `06_保守者向け/03_回帰テスト/check-docs.sh`（文書整合: INDEX 参照コスト・掲載漏れ・ケース数・参照切れ・目録同期） | ドキュメント記載と実ファイルの対応（目録同期）を機械的に照合する |

- 実行タイミング: 本体変更のたびに保守者が実行する（現行はキット自身の CI が手動起動のみのため、`.github/workflows/kit-ci.yml` を都度手動で回すか、コミット前にローカルで `ci/test-*.sh` を回す運用）
- 合格基準: `check-docs.sh` は NG=0 が合格。回帰テストは既知の既存 FAIL 件数（現行 Ver.8.0.0 時点: test-hooks 8・test-check-approval 37・test-check-docs 10・test-test-metrics 8）を超えないことを確認する運用を、案B移行時も踏襲する
- 監査記録の保存先: `internal/AUDIT-2026-07.md` 等の監査レポート（移行後 `06_保守者向け/`）に、実施日・NG件数・FAIL件数を記録する

## 7. 配布区分と管理の重さ

- 配布（案B: 01〜04）: 導入先（`~/.claude` またはプロジェクト直下）に配置される。変更時は CHANGELOG の互換性注記を必須とし、`install.sh` / `export-project.sh` / `verify.sh` の対応更新を変更管理の対象に含める
- 非配布（案B: 05〜06）: 保守者専用。変更管理は記録のみで足りる（承認は同じ保守者だが、他者へのレビュー義務は課さない）
- 00_導入（install / export 本体）: 配布物ではなく実行専用ツール。導入先には実行結果（配布物側のファイル）のみが残る（現行 README の「キットの checkout から実行する入口」の扱いを踏襲）
