# 開発速度ハーネス（順守必須）

所要時間 ≒ 往復回数 × 12秒。速度は「工程を削る」ではなく「往復を削る」で作る。
ゲート（pre-commit / verify-ui / 破壊操作の確認）は削らない。

出所: 実プロジェクトでの実測（2026-08-22〜23、UI 複数画面・実行系検証・共有資産変更の4タスク）。
知識がメモリにあっても参照されなかったため、本ファイルに集約し毎セッション読む。
プロジェクト固有の値は H-2 を各プロジェクトの `.claude/rules/speed-harness.md` で埋める。

## H-1. 着手前 3 行（必須出力）

最初のツール実行より前に出す:

```
目的: <1行>
見積: 自分 n 往復 + 委譲 m 本 × 上限 k 回（≒ X 分）
検証: <何を・何周で確認するか。既定は 1 周>
```

## H-2. 環境チートシート（その場で探索することを禁止。ここからコピーする）

プロジェクトごとに次を埋める。埋まっていない項目を作業中に探索したら、終了時に本節へ追記する。

```bash
# 起動（検証用: 認証オフ・ブラウザ自動オープンなし）
<起動コマンド>
# ヘルスチェック（待機ループを組まない）
curl -s --retry 15 --retry-delay 1 --retry-connrefused -o /dev/null -w "%{http_code}" http://127.0.0.1:<PORT>/
# 停止（pkill -f はコマンドライン不一致で効かないことがある。ポートで殺す）
kill $(lsof -ti:<PORT>) 2>/dev/null
```

- 編集の反映条件（再起動が要るか / ホットリロードか）: <記入>
- スクリーンショットの保存先: 最初から scratchpad の絶対パスを `filename` に指定する
- 認証・外部通信を止める手段: <記入>
- 既知の不具合・触ってはいけないファイル: <記入>

### 標準コマンド集（迷わずこれを使う）

| 場面 | 標準 |
|---|---|
| サーバ起動を待つ | `curl --retry N --retry-delay 1 --retry-connrefused`（待機ループを組まない） |
| 一時ファイルの片付け | `mv <対象> <scratchpad>/`（削除ではなく退避） |
| コミット対象の指定 | パスを明示して `git add <path...>`（`git add -A` を使わない） |
| PR の作成とマージ | 別々のコマンドとして順に実行（連結すると Base branch was modified で失敗する） |
| 複数ファイルの編集 | Read 全件 1 メッセージ → Edit 全件 1 メッセージの 2 往復に固定 |

安全フックに止められたら、安全装置が正しく働いた結果として受け入れ、標準コマンドに切り替える。

## H-3. UI 作業の型（バッチ検証）

1. **編集を全ファイル分まとめて**行う（1修正→1確認を回さない）
2. 再起動 1 回 → 対象画面のスクショを**連続で全部**取る → まとめて読む
3. 直しが出たら「全修正 → 1回検証」をもう 1 周。**上限 2 周。**
   3 周目が要る状態は設計不良。手を止めて報告する。

## H-4. 委譲の型

**発動条件:**

- 自分の往復 5 回以内で終わる作業は自分で行う（委譲の固定費 60〜90 秒/本の方が高い）。
- 超える見込みなら「最遅 1 本の想定時間」と「自分の往復 × 12 秒」を比べ、短い方を選ぶ。
  委譲する場合は起動前に見積もりと目的を 1 行で示す。
- **本数 = ファイル所有が重ならない独立作業単位の数。**粗い分割は必ず遅く、単位より細かく割っても速くならない。
  本数を増やしても完了は最遅 1 本で決まる。速くする唯一の手段は 1 本あたりのツール回数を絞ること。
- 1 本ごとにツール回数上限を明示する（既定 20 回。生成 1 ファイル: 5 回 / 複数ファイル配線: 15 回 / 調査: 18 回）。
- 全本を 1 メッセージで同時起動し、起動後の自分は委譲と重ならない作業（配線・検証準備）を進める。

**委譲プロンプトに必ず同梱するもの（2026-08-23 の失敗: 環境調査だけで上限を使い切って未達）:**

- H-2 相当の確定情報（URL 一覧・API 一覧・データ投入経路・既知不具合・禁止事項）と「再調査禁止」の明記
- 結果の書き出し先ファイルと、返却は 10 行以内の要約に限る旨
- 出力フォーマット（見出しレベルまで）。不備による再実行が最も高い

**役割分離:**

- **作った本人に検証させない。**生成系とは別に検証系（レビュー・仕様突合・構文/リンク検査）を 1 本以上含める。
- 検証系は生成後にしか走れないため、見積に**直列 90 秒**として織り込む。
- 検証系への指示は「合っているか」ではなく「壊れている箇所を探せ」で出す（確認バイアス回避）。

## H-5. 見積の既定に含めるもの（実測から）

| 項目 | 既定 | 出所 |
|---|---|---|
| 検証後の修正パス | +1〜2 分 | 2026-08-22: 未計上で 1.36 倍 |
| 実行系の実証を含む作業 | 1 実行の実測時間 × 周回数を先に足す | 2026-08-23: 68 ケース×2 回で 3.3 倍 |
| 共有ファイル（複数画面から参照される資産）への変更 | 回帰洗い出し 1 本 + 検証 1 本 + 修正パスで **+15 分** | 2026-08-23: 3.8 倍 |
| 検証の既定 | 代表画面のサンプリング。残りは「未検証」と明記 | H-3 |

## H-6. 違反時

見積の 1.5 倍を超えたら、原因 1 行を**本ファイルの実測記録に追記**してから完了報告する。
ルールの新設ではなく、H-1〜H-5 のどこで落ちたかを特定する。

## H-7. コミット・プッシュ・マージ

- ゲート（pytest / make test / verify-ui / lint）は**ユーザーが要求した時だけ実行する。**
  `claude-code/hooks/block-gates.py` が PreToolUse で強制する。要求があった時は `GATES_REQUESTED=1` を付けて実行する。
- 手順は一直線: add（パス明示）→ commit → push → PR 作成 → マージ（作成とマージは別コマンド）。
- コミット前に変更の性質（docs のみ / code / UI）を 1 行で確定させ、フック回避の要否をそこで決める。
- **ゲートが赤のときの最短手順**: 変更を stash した素の状態で同じ失敗が再現したら main 由来と断定し、
  それ以上の切り分けをしない。PR 本文に「main 由来・スコープ外」と 1 行書いて進む。

## H-8. 進捗の逐次提示（待たされていると感じさせない）

- **1 分超の見込み作業は開始時に必ず**: 本文に見積を宣言し、同じ bash に
  `python3 <hooks>/progress.py start "<タスク名>" <見積秒>` を連結する。
- **ステップ境界ごとに** `progress.py step "<n/m 名称>"` を既存コマンドへ連結する（専用の往復を作らない）。
- ツール実行の合間の本文は `[2/5 配線] 経過 1:20 / 見積 4:00・残り 2:40` 形式の 1 行進捗から始める。
- **完了時に必ず** `progress.py done` を連結する（消し忘れは偽の「実行中」表示になる）。
- 表示本体は `claude-code/hooks/statusline.py`（settings.json の `statusLine`）。タスクなし時は従来の `~/.claude/statusline.sh` へ素通しする。

## 実測記録（プロジェクトごとに追記）

形式: `- YYYY-MM-DD HH:MM〜HH:MM（タスク）: 実績 X 分 / 見積 Y 分（倍率）。原因: … 学び: …`
