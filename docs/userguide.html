AIDD Kit を初めて使う人のためのガイド

AI（Claude Code / Codex）に開発を頼むときの「進め方・品質チェック・見た目」を、毎回ゼロから考えなくて済むようにする個人用キットです。このページは「何が入っていて、どう始めるか」だけに絞っています。

対象: これから導入する人 所要: 読む 15 分 ＋ 導入 5 分 前提知識: ターミナルで cd と ls ができる 版: 6.3.0 → Ver.6.4 相当

iこのガイドについて

キットには説明文書が 3 種類あります。用途で使い分けてください。

文書読む人中身
このユーザーガイド（docs/userguide.html）初めて導入する人概要・導入手順・最初のセッション・毎日の流れ。まずここ
取り扱い説明書（docs/yuki-aidd-kit-manual.html）使い始めた人スキルの選び方・コマンド一覧・ECC との関係・プロジェクト別の使い分け・困った時（13 章）
README.md / INDEX.md中身を把握したい人版歴と全資産の地図（参照コスト付き）。AI もここを読む
spec/キット自体を改造する人全ファイルの読解記録・残課題・バックログ。spec/README.md から
このキットの基本姿勢

AI に丸投げする道具ではありません。仕様を決める → 実装する → テストする → 振り返る という流れを崩さず、「動いた」ではなく「確認した」で完了と言わせるための道具です。

?AIDD Kit とは

一言でいうと、AI 駆動開発（AIDD）の作業台です。次の 3 つを AI に渡します。

1. 進め方の規律

速度を最優先しつつ、目的の宣言・見積の実測・残課題の申告・未検証を「完了」と言わない、といった約束事。rules/ と AGENTS.md が担当。

2. 場面ごとの手順（スキル）

「テストをいつ回すか」「UI を作ったら何を確認するか」「振り返りをどう残すか」など、場面に応じて AI が自動で読む手順書。19 個。

3. 機械で止める仕組み

散文の約束は破られるので、秘密情報の混入・未検証 UI のコミット・要件と設計のズレ・CSS の直値などをスクリプトで検出します。

Ver.6.4 で何が変わったか（2026-09）

2026-10 の Claude Pro（Sonnet 基盤・Codex 併用）への移行に備えて、①入口スクリプトと git ゲートに回帰テストを付け、②毎回 AI が読む量を半分に減らし、③デザインを「散文」から「読み込むだけの CSS ファイル」に変えました。CI や定時実行のような自動処理は使わず、検査はすべて人が起動する方針です。

✓導入前の準備

  • Claude Code（CLI またはデスクトップ）か Codex のどちらか、または両方
  • git、bash、python3（3.10 以上。検査スクリプトが使う）
  • ターミナルで cd と ls ができること。それ以外は手順どおりコピーすれば動きます
先に決めておくこと

導入方式は 2 つあり、併用が前提です。自分の PC で複数プロジェクトを横断するなら A、Codex やクラウド環境・チームメイトの clone 先など ~/.claude が効かない場所には B。迷ったら A から始めてください。

A導入 A: 自分の PC に入れる（グローバル導入）

~/.claude/ にスキル・コマンド・hooks・rules・共通規約をコピーします。どのプロジェクトを開いても同じ規律が効きます。

  1. キットを取得する
    cd <作業フォルダ>
git clone https://github.com/ma-garin/yuki-aidd-kit.git
cd yuki-aidd-kit
  2. 導入スクリプトを実行する
    ./scripts/install.sh
    既存の ~/.claude/CLAUDE.md があれば .bak に退避し、既存の settings.json は上書きしません（hooks の設定は表示される内容を手でマージ）。同名の rules が別フォルダにある場合はスキップします。
  3. 配置を確認する
    ./scripts/verify.sh
    配置されたファイルの一覧と「導入済みの版」が出ます。✅ 全て正常 なら完了。1 つでも欠けていると exit 1 で止まります。
  4. （Codex も使う場合）AGENTS.md を共有する
    ln -s ~/.claude/AGENTS.md ~/.codex/AGENTS.md
    Claude Code は CLAUDE.md 経由で、Codex は直接、同じ本体を読みます。
  5. （任意）壊れていないことを回帰テストで確かめる
    ./scripts/test-hooks.sh          # hooks が入力を受け取れるか（19 ケース）
./scripts/test-install.sh        # 導入・配布・初期化（73 ケース。実 ~/.claude には触らない）
何が ~/.claude/ に入るか

AGENTS.md（共通規約の本体）、CLAUDE.md（@AGENTS.md を import ＋ Claude Code 固有）、rules/aidd-kit/*.md、skills/*/SKILL.md、commands/*.md、hooks/*、KIT_VERSION（版・commit・日付の刻印）。

B導入 B: プロジェクトに配る（プロジェクト配布）

対象プロジェクトの直下に .claude/ と AGENTS.md / CLAUDE.md を生成し、git に含めます。クラウドの Claude Code、Codex、チームメイトの環境でも同じ振る舞いになります。

  1. 配布する
    ./scripts/export-project.sh <対象プロジェクトのパス>
    生成物: .claude/（skills / commands / hooks / rules / settings.json / INDEX.md / templates）、AGENTS.md、CLAUDE.md、ゲート用スクリプト（scripts/quality_harness.py など）、.claude/KIT_VERSION。既存ファイルは .bak に退避します。
  2. コミットする
    cd <対象プロジェクトのパス>
git add .claude AGENTS.md CLAUDE.md scripts
git commit -m "chore: add AIDD Kit"
  3. プロジェクト固有の追記をする
    生成された AGENTS.md 末尾の「プロジェクト別追記欄」に、環境・起動コマンド・禁止事項を書きます。.claude/rules/speed-harness.md の H-2「環境チートシート」も埋めてください。
A と B の違い

中身は同じです。違いは置き場所だけで、B はリポジトリに同梱されるので環境を選びません。両方入れた場合、プロジェクト側（B）の設定が優先されます。

新規プロジェクトをゼロから作るとき

./scripts/init-project.sh my-app pwa        # pwa | html | streamlit
./scripts/init-lifecycle.sh <対象> --github  # 工程文書 11 本＋Issue/PR テンプレート（納品案件のみ）
./scripts/init-test-docs.sh <対象> --ci     # テスト戦略・DoD・29119 文書・機能契約・ゲート（QA 案件のみ）

1最初のセッション

導入が済んだら、プロジェクトのフォルダで Claude Code（または Codex）を起動します。何も指示しなくても、共通規約と rules は自動で読み込まれています。

AI が最初に見ているもの

  • AGENTS.md の「読む範囲」表 — やりたいこと（UI を作る・テスト・完了判定…）から、最初に使うスキルを引く
  • rules/absolute-rules.md — 着手前に 目的: を 1 行、提出時に 残課題:、未検証を「完了」と言わない
  • rules/speed-harness.md — 往復を減らす見積と手順設計。ゲート（テスト・lint）はあなたが頼んだ時だけ実行
  • rules/model-routing.md — 既定は Sonnet。Opus に上げる条件、/clear の目安

最初の一言の例

このプロジェクトに合う ECC だけ選んで        # 何を毎回読み、何を必要時だけ読むかを分けてもらう
このプロジェクトの spec / plan / tasks を作って   # /sdd-start 相当。仕様駆動で始める
管理画面のダッシュボードを作って              # design-system が発火し、tokens/components/layout を読み込む形で作る

実装モードという考え方（Claude Code のみ）

  1. /plan で方針を固める
    調査（Read / Grep / Glob）が許可された状態。方針・対象ファイル・検証手順を PLAN.md に書き出す。
  2. /implement で実装に入る
    .claude/mode が作られ、hook が再探索を物理的にブロックする。決めたとおりに小さく作り、軽くテストする。PLAN.md が無いと入れない。
  3. 完了前に done-gate
    実行経路（UI → API → 保存 → エラー処理 → 利用者に見える証跡）を確認し、未検証は「未検証」と書く。UI を触ったら uiux_review で実機を開く。
よくあるつまずき

「hook にブロックされた」と出たら実装モードです。調べ直したいときは /plan で解除してください。テストを回してほしいときは「テストを実行して」と明示します（黙って走らせない設計です）。

↻毎日の流れ

やりたいことを言えば該当スキルが発火します。名前を覚える必要はありませんが、表を知っていると狙って使えます。

やりたいこと言い方の例裏で効くもの
進め方を決める「この案件は工程を分けるべき？」dev-lifecycle の判断表。分けるなら /rfd → /lifecycle → /trace、軽い案件は /sdd-start
UI を作る・直す「設定画面を作って」「ボタンの見た目を揃えて」design-system（tokens / components.css / layout.css を読み込む）→ 完了前に uiux_review
テストをいつ・どう回すか「このプロジェクトのテスト戦略を決めて」test-strategy → コードは test-automation → E2E は /e2e-cycle
レビュー・品質判定「ISO 25010 でレビューして」qa-review-standards（/qa-review）。「まだおかしい」の根こそぎは atarimae-quality-audit
完了と言う前「完了判定して」done-gate
長い調査・集計「ログを全部見て傾向を出して」context-compression（/compact-work）。3 層要約・スクリプト化
振り返り「今日のレトロをやろう」retro（/retro）→ lessons.md に Keep / Problem / Try
AI 出力の評価「RAG の回答品質を回帰評価したい」agent-eval（/eval）
表に無い・迷った「INDEX を見て」INDEX.md（全資産の地図。毎回は読まない）

セッションの終わり方

  • CURRENT_STATE.md（フェーズ・直近完了・次タスク・判断待ち）を更新してもらう
  • 無関係なタスクへ移るときは /clear。1 時間以上空けて再開するときは要約から始める（キャッシュが切れて全履歴を読み直すため）

$Pro / Sonnet で使うコツ

キットは Claude Pro（Sonnet 基盤）でも快適に回るように作り直してあります。押さえるのは 4 点です。

  1. 毎回読まれる量は小さい — 共通規約 ＋ rules 3 本で済むよう圧縮済み（推定で従来の半分）。/context で何が載っているか確認できます
  2. 既定は Sonnet、上げるのは 3 条件だけ — 複数モジュールにまたがる設計判断／多段の推論が要る不具合の切り分け／Sonnet が 2 周しても収束しない。上げる前に「何を判断させるか」を 1 行書き、終わったら戻す（rules/model-routing.md）
  3. 定型作業は effort を下げる — 文書の整形・調査結果の要約・既知手順の反復は /effort で下げる
  4. 上限に当たったら — 「セッション上限」「週次上限」は全モデル共有で /model では回復しない。「Opus 上限」「Sonnet 上限」は系列別なので切り替えて続行。まず /usage で内訳を見る
読ませて、書かせない

デザインの CSS や工程文書の雛形は実ファイルとして同梱してあります。Sonnet に書き起こさせるのではなく、読み込む指示を出す形にすると、ブレず安く済みます。

Codex には /model /effort /usage がありません。モデル選択の設定で同じ判断をし、委譲の規律と「新しい会話で始める」だけ守ります。

◐画面の見た目を揃える

キットのデザインシステムは「散文の指示」ではなく読み込むだけの CSSです。値の唯一の真実源は templates/tokens.css。

Qよくある質問

Q. 導入したのに AI がスキルを使ってくれない

./scripts/verify.sh で配置を確認してください。スキルは「UI を作る」「テスト戦略」など説明文に書かれた言葉で発火します。狙って使うなら「design-system スキルで」と名前を言うか、対応するスラッシュコマンドを使います。

Q. テストを勝手に回してほしいのに拒否される

仕様です（block-gates.py）。「テストを実行して」と明示してください。AI は GATES_REQUESTED=1 を付けて実行します。

Q. 「hook にブロックされました」と出た

実装モード中（.claude/mode がある）に調査系ツールを使おうとしています。/plan で解除するか、方針が固まっているなら実装を続けてください。

Q. 既存の ~/.claude/settings.json があった

install.sh は上書きしません。表示される hooks 設定を手でマージしてください。プロジェクト配布（B）なら .claude/settings.json を生成するので手作業は不要です。

Q. キットを更新したい

git pull のあと ./scripts/install.sh && ./scripts/verify.sh。配布先は ./scripts/export-project.sh <対象> を再実行（既存は .bak に退避）。どの版から出たかは ~/.claude/KIT_VERSION または .claude/KIT_VERSION に刻印されています。

Q. 完了報告に「未検証」と書かれている

正常です。確認していないことを「完了」と言わない規律（A-6 / functional-integrity）です。必要なら「テストを実行して検証して」と頼んでください。

Q. 自分のプロジェクトに CI を入れたい

github-actions/ の 4 本を .github/workflows/ にコピーします。いずれも手動起動（Run workflow）のみで、PR や push では走りません。自動化したい場合は自分の判断で on: を書き換えてください。
