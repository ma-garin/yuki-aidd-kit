## OPS-NEW-03

### 事象（引き継ぎ文）
憲法ゲートの解除手順は「保守者が自分の端末で停止 file を消し、停止時刻より新しいインシデント記録を書く」。クラウドの一時コンテナには保守者のローカル端末が無く、この手順をそのまま実施できない可能性がある。

### 確認できた仕組み（コードで確かめた範囲）

解除手順の定義
- 停止 file は `<プロジェクト root>/.claude/constitution-stop`。環境変数 `AIDD_STOP_FILE` で場所を変えられる（`constitution-gate.py:66-70`）。
- 付随ファイル（同 `:69-70`）:
  - `.last`: 停止時刻（先頭列は epoch）
  - `.claude/constitution-state.json`: 状態
  - `.claude/constitution-violations.jsonl`: 違反記録
- 停止中は PreToolUse が全ツールを deny する（`:289-293`）。Stop hook は停止中なら素通りで、番を終えて保守者に渡す（`:324-325`）。
- 再開の判定は 2 段（`:289-302`）:
  1. 停止 file が存在しない。
  2. `.last` が在るとき、インシデント記録の file の mtime が停止時刻より新しい。記録 file は `06_保守者向け/学んだこと.md`、無ければ `docs/lessons.md`、無ければ `.claude/lessons.md`（`:72-74`）。判定は mtime だけで、内容は見ない。
- 手順 3 点は設計文書にも同じ（`constitution-gate.md:34-37`）。
- 「解除の環境変数は作らない」: `constitution-gate.py:4`、`constitution-gate.md:11`。意図は、事故（2026-11-03 の見積欠落 3 回・無報告 2 回）で「気をつける」「規約」が効かなかったので、AI の判断・出力から切り離した制御にするため（`constitution-gate.md:4-7`）。環境変数やツール引数で解除できると、AI 自身が設定できる。
- 環境変数として存在するのはテスト用だけ（`AIDD_NOW_EPOCH`、`AIDD_TRANSCRIPT_FLUSH_SEC`）。`AIDD_STOP_FILE` は場所の変更で、解除ではない（`:8`、`:66`）。ただし AI が起動時環境を握れる状況では場所を変える抜け道になりうる（未検証。下記）。

停止中に AI が停止 file・状態 file を触った場合
- 停止中はそもそも全ツールが deny（`:289-293`）。この分岐は `tampers` 判定より前なので、停止中の触る試みは違反記録を増やさない。deny だけ。
- 停止していない状態で `Write`/`Edit`/`MultiEdit`/`NotebookEdit` が停止 file・`.last`・状態・違反記録のいずれかを対象にすると、改ざん扱い（`:277-284`）。違反 `停止 file の改ざん` として、停止 file を書いて deny する（`:294-296`）。
- Bash は保護名（`constitution-stop`・`constitution-state`・`constitution-violations`・停止 file 名）を含み、読み取り専用と確定できないと改ざん扱い（`:45-55`、`:269-275`）。読み取り（`cat` `grep` `ls` 等の並べただけ）は許可。
- 限界: 保護名を含まない削除（`.claude` ごと・glob・変数組み立て等）は判定されない（`:9-13`、`constitution-gate.md:25`）。これは本 ID の対象ではなく、ロードマップ M25 の既存項目。

クラウドで、この手順を誰がどう実行できるか（コードの範囲）
- 手順 1（停止 file を消す）: 停止 file はコンテナ内のファイル。実行できるのは AI のツールだけだが、停止中は全ツール deny、改ざんは違反。保守者がコンテナのシェルを持つ経路を、実装は用意していない。
- 手順 2（インシデント記録を書く）: 記録 file は git 管理下のリポジトリ内ファイル。停止中は `Write`/`Edit` も deny される（Read・Grep・Glob も deny。`READ_ONLY` の免除は見積ゲートだけで、停止中の分岐には無い。`:195`、`:289`）。
- 解除用の入口は実装に無い。UserPromptSubmit・SessionStart に停止解除を行う処理は配線されていない（`.claude/settings.json` の PreToolUse・Stop・SessionStart は、憲法ゲート・計測・読み取りガード等。`constitution-gate.py` は `pre`・`stop`・`report` の 3 モードだけで、解除モードを持たない。`:352-371`）。`report` は表示だけ（`:335-350`）。
- つまり「人間の入力だけから解除できる」経路は、ローカルの端末操作（rm と file 編集）に限られる。クラウドで同等の経路は実装にも文書にも無い。

### 改善の方向（実装しない。方向だけ）

論点:
- ローカルとクラウドで復旧経路を分ける。クラウドは「解除」でなく「新しいセッションの開始」を復旧とするのが素直。
- 正規の権限を持つ保守者が、AI 経由でない入力で解除できること。
- 解除不能時は、停止・報告・退避の手順を定める。
- 不正な回避経路（AI が書ける環境変数・ツール引数・出力文字列）を作らない。

条件「AI の出力・ツール引数・環境変数からは解除できず、人間の入力だけから解除できる」を満たす案:

| 案 | 内容 | 損益 |
|---|---|---|
| A 新セッション開始で解除 | クラウドは停止状態を持ち越さない。停止 file はコンテナ内のみ、記録は違反を push 済みの issue/PR に残す | コスト小。取り消しは新セッションを作り直す。放置すると、破棄で停止も記録も消える（現状と同じ） |
| B 人間の UserPromptSubmit 入力で解除 | 利用者の発言に決まった承認語があるときだけ hook が停止 file を消す。transcript の人の発言だけを見る（`instruction_of` 流用可） | コスト中。語の偽装・貼り付け経由の混入を要検討。取り消しは容易。放置するとクラウドは停止したまま使えない |
| C リポジトリ外の保守者承認 | 外部の承認（PR の承認、ブランチ保護された file）が新しく入ったときだけ解除 | コスト大。外部への依存が増える。取り消しは困難。放置すると、クラウドは復旧不能 |

推奨: A。理由は次の通り。
- 既存の設計「解除の経路を作らない」に最も整合する（AI の入力から解除経路を増やさない）。
- 実装が最小。停止直前に成果物を push する手順（事前の退避）を規約として添えるだけ。ただし停止中は git も deny なので、退避は「違反の検知前」「違反の直前」に行うしかない。この点は未解決で、B を併用するか別途設計が要る（要判断）。
- B は有望だが、人の発言かどうかの判定（`instruction_of`、`:106-122`）が transcript の tail 2 MB に依存する（`:28`、`:124-135`）。偽装耐性を実測してから決める。
