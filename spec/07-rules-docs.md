## `absolute-rules.md`（112行）— A-1〜A-10

冒頭: 「**例外なし。状況で緩めない。守れないなら着手せず、その旨を報告して止まる。**」
各ルールは「いつ発動するか」と「何を出力するか」を持つ（**出力に現れない工程は必ず落ちる**ため全て可視化する）。

| ID | 発動 | 出力 | 要点 |
|---|---|---|---|
| A-1 | 指示直後・最初のツール呼び出しより前 | `目的: ...` | 表面の動詞でなく**誰が・なぜ・今それを求めているか**から逆算。「表で出して」は見せろでなく管理せよ、「調べて」は集めろでなく検証せよ |
| A-2 | 2分超の作業の前 | 見込み・実績・差異の3列表 | 開始時に `date +%H:%M:%S`。**測らない見積もりは出さない**。実績を体感で埋めない。未計測なら「未計測」と書く |
| A-3 | 成果物を提示する直前 | `残課題: ...`（1〜3行） | 「自分がレビュアーならまずどこを突くか」。品質の主張でなく指摘を書く。**「作った」を「終わった」と扱わない** |
| A-4 | 一覧・計画・分類・チェックリストを作るとき | 照合した外部基準の名前 | 記憶からの列挙は必ず漏れる。ISO/IEEE・PMBOK・ISTQB 等**外部の体系に照らす**。自作の枠組みを確立された分類のように提示しない |
| A-5 | 事実・数値・因果を述べるとき | 根拠、または「未検証」「未確認」 | 一次資料で確認できない数値を使わない／観測数が少ないものに因果を主張しない／**批判されたときに検証せず前言を撤回しない**（過剰な譲歩は不誠実） |
| A-6 | 調査の結論を出した後、実装・設計へ進むとき | その判断が調査結果のどれに基づくか | 「X が最重要」と結論したなら**X を検証せずに先へ進まない**。失敗の主因は知識不足でなく、知っていることを自分の成果物に適用しないこと |
| A-7 | 設計文書を提出したとき | 承認待ちである旨＋承認と独立に進められる作業 | 品質ゲートを自分で書いて自分で飛ばさない。進めてよいのは**契約が確定していて手戻りが発生しない範囲**のみ |
| A-8 | バックグラウンド処理の起動時 | 見積もりを超えた時点での生存確認結果 | 完了通知が来ないことを「動いている」と解釈しない。数分進捗が無ければ停止し軽量版で再実行。**指摘される前に自分から確認** |
| A-9 | 常時 | 既定3行。超えるなら冒頭に理由を1行 | 分析・経緯・弁明は求められない限り書かない |
| A-10 | 重い処理・大量の並列実行の前 | 見積もりと短縮案 | 利用上限は有限。**正確性のために時間を使う判断は先に許可を取る** |

**守れなかったとき**: 言い訳をせず、何を破ったか・なぜ破ったかを1〜2行で述べ成果物を訂正する。
**再発防止としてルールを新設せず、既存ルールのどこで落ちたかを特定する。ルールを書くこと自体を対処として扱わない。**

## `speed-harness.md`（115行）— H-1〜H-8

前提: **所要時間 ≒ 往復回数 × 12秒。速度は「工程を削る」でなく「往復を削る」で作る。ゲート（pre-commit / verify-ui / 破壊操作の確認）は削らない。**
出所: 実プロジェクトでの実測（2026-08-22〜23、UI 複数画面・実行系検証・共有資産変更の4タスク）。
*知識がメモリにあっても参照されなかったため、本ファイルに集約し毎セッション読む*。

| ID | 内容 |
|---|---|
| **H-1** | 着手前3行（必須出力）: `目的:` / `見積: 自分 n 往復 + 委譲 m 本 × 上限 k 回（≒ X 分）` / `検証: 何を・何周で（既定1周）` |
| **H-2** | 環境チートシート。**その場で探索することを禁止し、ここからコピーする**。起動コマンド／`curl --retry 15 --retry-delay 1 --retry-connrefused` によるヘルスチェック（待機ループを組まない）／`kill $(lsof -ti:<PORT>)`（`pkill -f` はコマンドライン不一致で効かないことがある）／反映条件／スクショ保存先／認証停止手段／既知の不具合。**埋まっていない項目を作業中に探索したら終了時に追記する**。標準コマンド集5行（`git add -A` を使わない／PR 作成とマージは別コマンド／複数ファイルは Read 全件1メッセージ→Edit 全件1メッセージの2往復に固定）。**安全フックに止められたら、安全装置が正しく働いた結果として受け入れる** |
| **H-3** | UI 作業の型（バッチ検証）: ①編集を全ファイル分まとめて ②再起動1回→スクショを連続で全部→まとめて読む ③直しが出たら「全修正→1回検証」をもう1周。**上限2周。3周目が要る状態は設計不良で、手を止めて報告する** |
| **H-4** | 委譲の型: 5往復以内なら自分でやる（委譲の固定費60〜90秒/本）／**本数＝ファイル所有が重ならない独立作業単位の数**（完了は最遅1本で決まる）／1本ごとにツール回数上限（既定20・生成1ファイル5・複数ファイル配線15・調査18）／全本を1メッセージで同時起動。**委譲プロンプトに必ず同梱**＝H-2 相当の確定情報と「再調査禁止」・書き出し先と10行以内の要約・出力フォーマット（*2026-08-23 の失敗: 環境調査だけで上限を使い切って未達*）。**役割分離＝作った本人に検証させない**。検証系は直列90秒として見積に織り込み、指示は「合っているか」でなく**「壊れている箇所を探せ」**（確認バイアス回避） |
| **H-5** | 見積の既定に含めるもの（実測から）: 検証後の修正パス +1〜2分（未計上で1.36倍）／実行系の実証は「1実行の実測×周回数」を先に足す（68ケース×2回で3.3倍）／**共有ファイルへの変更は +15分**（回帰洗い出し1本+検証1本+修正パス。3.8倍）／検証の既定はサンプリングで残りは「未検証」と明記 |
| **H-6** | 違反時: 見積の1.5倍を超えたら原因1行を**本ファイルの実測記録に追記**してから完了報告。ルール新設でなく H-1〜H-5 のどこで落ちたかを特定 |
| **H-7** | **ゲート（pytest / make test / verify-ui / lint）はユーザーが要求した時だけ実行する**（`block-gates.py` が PreToolUse で強制。要求時は `GATES_REQUESTED=1`）。手順は一直線（add パス明示→commit→push→PR 作成→マージ）。**ゲートが赤のときの最短手順**: 変更を stash した素の状態で同じ失敗が再現したら main 由来と断定し、それ以上切り分けない |
| **H-8** | 進捗の逐次提示: 1分超の見込み作業は開始時に見積を宣言し `progress.py start` を同じ bash に連結／ステップ境界ごとに `step`（専用の往復を作らない）／本文は `[2/5 配線] 経過 1:20 / 見積 4:00・残り 2:40` 形式の1行から始める／**完了時に必ず `done`**（消し忘れは偽の「実行中」表示） |

## `functional-integrity.md`（41行）

- 必須の検証経路: `UI → API → backend route → service/core → output → persistence → error handling → user-visible evidence`

- Critical / High リスク機能では必ず確認: happy path / failure path / timeout・cancellation / auth・login wall / robots・制限 / partial result・recovery / ログまたは証跡 / ユーザーに見えるエラー・状態表示

- **プロセス上の失敗には名前のある RCA 枠組みを使う**（5 Whys / Fishbone / FMEA / CAPA / DoD 更新）。枠組み名を持たない場当たりの原因分析は禁止
