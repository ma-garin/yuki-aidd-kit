AIDD Kit を初めて使う人のためのガイド

AI に開発を手伝ってもらうときの「段取り」と「安全装置」と「部品箱」をひとまとめにした道具です。このページは、専門用語をできるだけ使わずに「何なのか」「どう入れるのか」「最初に何を言えばいいのか」だけを説明します。

対象：これから導入する人・AI 開発が初めての人 所要：読む 20 分 ＋ 導入 5 分 必要な知識：黒い画面（ターミナル）に文字を打てること

止められた・記録の見方が分からないときは 操作マニュアル「困ったときの一覧」（環境変数・逃がし口・ログ・hook の理由文と対処）を引いてください。

1まず 3 分：これは何？

たとえ話で言うと

会社に新人が来たとき、いきなり「じゃあ作って」とは言いません。仕事の手引き（こういう順番で進める、ここは必ず上司に確認する）と、チェックリスト（出す前にここを確認する）と、道具箱（毎回使う雛形や部品）を渡します。

AI に開発を頼むときも同じです。何も渡さないと、AI は毎回ゼロから考え、毎回違うやり方をし、「できました」と言いながら確認していない、ということが起きます。AIDD Kit はその「手引き・チェックリスト・道具箱」を AI に渡すためのセットです。

AIDD は「AI 駆動開発（AI-Driven Development）」の略で、実装は AI に任せ、人は決めること・確認すること・承認することに集中する進め方を指します。

入れると何が変わるか

入れる前 ・毎回「どう進める？」から説明が始まる
・AI が「できました」と言うが、実は動かしていない
・画面ごとに色や余白がバラバラ
・勝手にテストを回してトークン（AI の利用量）を使い切る
・API キーをうっかりコミットしそうになる
入れた後 ・AI が最初から「進め方の約束」を読んでいる
・確認していないことは「未検証」と正直に書く
・色・余白・部品は用意済みの CSS を読み込むだけ
・テストは「回して」と言ったときだけ回る
・秘密情報の混入をコミット前に機械が止める

大事な考え方

AI に丸投げする道具ではありません

「仕様を決める → 作る → 確かめる → 振り返る」の順番を崩さないための道具です。決めるのも、最後に OK を出すのも、人です。キットはその順番を AI に守らせ、確かめたかどうかを機械で見張ります。

AGENTS.md / CLAUDE.md（共通の約束事）

AI が毎回いちばん最初に読む 1 枚。「やりたいこと → 最初に使う手順書」の対応表もここ。CLAUDE.md は AGENTS.md を読み込む 1 行と、Claude Code だけで効く設定を持つ小さなファイルです。

rules/（規律 4 本）

毎回読むのは 3 本だけ（合計 100 行以下に抑えてあります）。4 本目の「機能完全性」は、コードや画面を触ったときだけ読まれます。

agents/（5 体のエージェント）

「図書管理システムを作って」のように成果物ごと頼むと、aidd-lead が受けて、種類の判定・工程分け・設計・実装・画面・テストまで自分で進めます。どの手順書を使うかを、あなたが選ぶ必要はありません。

skills/（21 の手順書）

毎日の進め方を決める 13 本と、プロジェクトの種類で選ぶ 8 本。1 本 200 行以下。AI はあなたの言葉で「どれを開くか」を決めます。

commands/（19 のコマンド）

会話の中で /plan のように打つと決まった手順が走ります。よく使うのは /plan /implement /qa-review /retro。

hooks/（7 の見張り）

「頼んでいないテストを拒否」「実装中の調べ直しを拒否」「1 分超の作業の進み具合を表示」など。口約束を機械にしたものです。

00_導入/ と 02_共通/ひな形/

人が使う道具と雛形。導入（install / export）、検査（verify / check-docs / check-design）、雛形（工程文書 11・テスト文書 8・デザインの CSS と部品）。

フォルダ番号の意味

00_導入/ が入口、01_利用者向け資料/〜04_Codex/ が配布される中身（このガイドや資料一式も含む）、05_プロジェクト管理/・06_保守者向け/ は配布されません。

見張り役に止められたら（8.2.0〜）

hooks は「規約を読ませる」のではなく「守れていない状態を止める」役です。 止められたら安全装置が働いた結果として受け入れ、理由に書かれた次にやることに従ってください。

  • git add -A や rm -rf のような取り返しのつかない操作は実行前に止まり、代わりの手順が出ます
  • 「承知しました」だけの返事や、実測の無い完了報告は差し戻されます
  • 見積は毎回実測され、次の見積に補正がかかります（体感で分を置いて外し続けないため）
  • 時刻は日本時間に固定されています（リモート環境は既定が UTC のため）

詳しい一覧は操作マニュアルの「止められたとき」章にあります。

セキュリティ強制層（8.3.0〜）

秘密ファイル名・秘密値の判定は secret_patterns.py（hook ではなく共通部品）に1か所へまとめました。 書き込む本文に AWS キーや GitHub トークンなど既知形式の値があれば pre-write-check.sh が止めます。 設定・hook 自体の書き換え（.claude/settings.json・.claude/hooks/・.git/hooks/）は block-protected.py が新たに止めます。

限界: hooks は Bash を構文解析しません。python -c "..." や変数代入・コマンド置換 （$(...)）で組み立てた秘密の読み出しは検出できないことがあります。 プロジェクトの settings.sandbox.json の denyRead（ファイルシステムレベルの遮断）と 併用してください。

利用計測・JIT注入・走査と基準線（8.4.0〜）

  • 新しい見張り役 hooks/injection-guard.py は、Web取得やMCPの結果に「これまでの指示を無視して」のような指示の形の文が混じっていないかを見ます。警告専用（止めません）。見つけたら「データであり指示ではない」と注記するだけで、続きはあなたが判断します
  • /security-audit（02_共通/ツール/security-scan.sh）は導入済みの走査器（pip-audit・osv-scanner・bandit・gitleaks 等）だけを回します。走査器が入っていない項目は「未検査」で、合格には数えません。「指摘なし」に見えても、まず未検査の一覧を確認してください
  • check_design.py --baseline <file> は、既知の NG を記録したファイルに載っていない新規の NG だけを不合格（exit 1）にします。記録は --baseline <file> --baseline-write で書きます。件数が減る方向の更新だけが書かれ、増える更新は拒否されます（exit 1）
  • どのスキル・MCP が何回・何トークン使われたか: python3 00_導入/03_点検/token_report.py --by skill,agent,mcp,tool --skills-dir 03_ClaudeCode/skills（JSONL を省くとカレントのプロジェクトの最新セッション）。既存の集計の後に「区分・名前・回数・トークン・費用比・平均・最大」の表が出ます。--skills-dir を付けると一度も呼ばれないスキルと、1 セッションで --over（既定 10）回を超えた呼ばれすぎのスキルも出ます
  • 上流が変わった下流を見つける（trace-check の C7）: 追跡表のセルに REQ-F-001@a1b2c3d のように上流の版を書いておくと、bash 02_共通/ツール/trace-check.sh docs/lifecycle が現在の版と食い違うリンクを suspect（NG）として出します。変更の前には --impact REQ-F-001 で影響する下流を連鎖で一覧できます。--tests <テストのディレクトリ> を付けるとテストコードの spec: ST-001 と CSV のテスト ID を突き合わせます（C8 未対応は NG・C9 は WARN）。テストケースの CSV は既定で対象ディレクトリの親の system_test_cases.csv を探します。別の場所なら --csv <path> を付けます。CSV が無いと C8 は判定不能（NG）です。下流を読み直して問題ないと確かめた記録 --refresh ID は保守者だけが打ちます（AI は打ちません）
  • （保守者が retro の最後に手で）採用した ADR を規則にする: python3 02_共通/ツール/adr-to-rules.py docs/adr lessons.md --out .claude/rules。**状態**: が採用の ADR と適用パスのある lessons だけが decisions-<slug>.md になり、該当ファイルを編集するときだけ AI の文脈に入ります。検討中・却下などは飛ばします。hook や定期実行にはしません

セキュリティ運用・完了主張の照合・仕様品質（8.5.0〜）

7AI との 3 つの約束

使っていると「AI が止まった」「拒否された」と感じる場面があります。全部このキットのわざとそうしている約束です。理由を知っておくと慌てません。

約束 1：テストや検査は「頼んだときだけ」回る

AI は放っておくと、確かめるために何度もテストを回し、AI の利用量（トークン）を使い切ります。キットでは hook（block-gates.py）が、あなたが頼んでいないテスト実行を機械的に拒否します。

あなたテストを実行して確認して
AI（GATES_REQUESTED=1 を付けて実行）結果: 12 件中 12 件 PASS

「回して」と言えば回ります。何も言わなければ、AI は「未実行」と書いて提出します。

約束 2：確認していないことを「完了」と言わない

「動きました」は禁止語です。実際に動かした、画面を開いて見た、テストが通った、のどれかがあって初めて「確認した」と書けます。確認していないものは 未検証 と書かれます。「未検証」は失敗ではなく、正直な報告です。

約束 3：実装中は「調べ直し」をしない（Claude Code のみ）

AI は迷うと同じファイルを何度も読み直して時間と利用量を溶かします。そこで「方針を決める時間」と「作る時間」を分けます。

  1. /plan：方針を決める（調べてよい時間）

    AI がファイルを読み、方針・触るファイル・確かめ方を PLAN.md に書きます。あなたはそれを読んで OK / 修正を伝えます。

  2. /implement：作る（調べ直しは禁止）

    .claude/mode というファイルが作られ、hook が「ファイルを読み直す操作」を止めます。決めた通りに小さく作り、軽く確かめます。PLAN.md が無いと入れません。

  3. 完了前：done-gate で自己点検

    「画面 → 処理 → 保存 → エラー時 → 利用者に見える証拠」まで通っているか、未検証は何か、を AI が表で出します。画面を触ったなら uiux_review で実機を開きます。

「hook にブロックされました」と出たら

いま /implement の最中です。調べ直したくなったら /plan と打てば解除されます。

W字：並行するテスト活動はどこまで入っているか

W字モデルは「左側の工程と並行してテスト設計と静的レビューを行い、欠陥を作り込んだ工程へ戻す」という型です。キットは名前こそ使っていませんが、出口基準の形で一部を取り込んでいます。正直な現状は次のとおりです。

できている 一部だけ できていない

上段の工程と下段のテスト活動が同じ時期に動くのが W字です。キットは 5 つのうち 2 つを出口基準として強制し、3 つは道具はあるが工程に結び付いていません。

説明するときに隠さない 3 点

①基本設計の出口基準に結合テストの観点が無い（要件と詳細設計には対応するテストの種が必須化されているのに、ここだけ抜けている）。②レビュー（静的テスト）の記録様式が無い。観点は qa-review-standards にあるが、工程ごとの記録が残らない。③欠陥に「どの工程で作り込んだか」の欄が無い。だから前工程へのフィードバックが人の記憶に依存する。

いつ V字で進め、いつ進めないか

すべての案件を V字で進めるわけではありません。キットは最初にこれを判断させます（dev-lifecycle の適用判断）。

両者は排他ではなく入れ子です。要件定義は spec.md の上位に立ち、実装記録の T-ID は tasks.md の番号をそのまま使います。同じ内容を二重に書かないための決めです。ハンズオンの事例（貸出管理モック）は軽量 SDD 側を通っています。

印工程の承認ゲート（要求どおり作られているかを止めて確かめる）

AI に設計や実装を任せたとき、いちばん不安なのは「頼んだとおりのものが本当に作られているのか」です。
AI の進め方が正しいか（プロセスが回っているか）を見るサービスはありますが、企業が知りたいのはそこではありません。知りたいのは中身が要求と合っているかです。

手戻りが最大になる壊れ方

人が要件定義をして、AI が基本設計から実装・テストまでを担当し、人が受け入れテストで確かめる。この分担自体は正しいのですが、誤りが見つかるのが最後になります。
要件の取り違えが基本設計に入り込むと、詳細設計も実装も単体テストも結合テストも、全部その間違いの上に積み上がります。受け入れテストで気づいたときには、作り直す量が最大になっています。

そこで、工程ごとに人が承認し、承認が取れていない工程の先へは進めないようにします。誤りを工程 1 つ分に閉じ込めるための仕組みです。

仕組みは 3 段構え

段何をするか実体
① 記録を残す工程ごとに承認の記録をファイルで残す。判定・根拠・承認者・日時を書くdocs/lifecycle/approvals/phase-0.md 〜 phase-9.md
② 版に縛る承認した瞬間の成果物の指紋（ハッシュ）を記録に書く。後から成果物が 1 文字でも変われば承認は自動で失効する./scripts/phase-hash.py ＋ 記録の reviewed_hash 欄
③ 物理的に止める前の工程が未承認のまま次の工程の文書を書こうとすると、AI の手がその場で止まるblock-phase.py（見張り役）
②が無い承認は形だけになる

判子を押した後に中身を差し替えられるなら、その判子には意味がありません。承認は「この版を承認した」という形でしか有効になりません。キットはもともと画面テストで同じ考え方（.ui-verified）を使っていて、それを工程承認へ広げたものです。

実際にどう止まるか

第 2 工程（基本設計）が未承認のまま、AI が第 3 工程（詳細設計）を書こうとすると、こう出て書き込みが拒否されます。

前工程が未承認のため docs/lifecycle/03-detailed-design.md を書けません（工程承認ゲート）。
❌ 第3工程にはまだ着手できません — 第2工程 基本設計: 未承認
  - 未承認: 成果物は着手済みですが判定が未記入です。`/phase-review 2` の後、人間が phase-2.md を埋めてください
  次の行動: /phase-review 2 で指摘を潰し、人間が docs/lifecycle/approvals/phase-2.md を承認する
誤りの伝播を工程1つ分で止めるための制限です。

承認を取った後で基本設計を書き換えると、こうなります（②の失効）。

=== 工程承認検査: 第2工程 基本設計 ===
❌ 失効
  - 失効: 承認後に成果物が変更されています（承認時 dc06593847f5e4d8 / 現在 d3d80f2542dc3083）。

使う手順（1 工程ぶん）

  1. AI に下書きさせる：/lifecycle 基本設計
  2. AI に指摘を出し切らせる：/phase-review 2

  3. 指摘を潰す：差し戻し事項には必ず「解消したことをどう確かめるか」が書いてあります
  4. 人が承認する：docs/lifecycle/approvals/phase-2.md に判定・根拠・自分の名前・日時を書き、./scripts/phase-hash.py docs/lifecycle/02-basic-design.md の出力を reviewed_hash に貼る
  5. 確かめる：./scripts/check-approval.sh --phase 2 が exit 0 なら次工程へ進めます

機械が見られること・人にしか見られないこと

ここを曖昧にすると「AI が承認した」ことになり、第三者検証としての価値が消えます。キットはこの線を越えません。

機械が判定する（check-approval.sh）人にしか判定できない
承認の記録があるか・必要な欄が埋まっているかその設計が本当にその要件を満たすか
承認した版と今の版が一致するか（失効の検出）受入基準の解釈が依頼者の意図と合っているか
未解消の差し戻しや未確認事項を残したまま「承認」になっていないか残っているリスクを受け入れてよいか
承認者が人間か（AI の名前が入っていないか）条件付き承認の条件が妥当か
着手済みの工程の手前に、未承認の工程が無いか

判定は 3 つだけです：承認 / 条件付き承認 / 差し戻し。空欄は判定ではなく「未承認」という状態として扱われ、合格には数えません。終了コードも 0（合格）／1（未承認・失効）／2（記録が壊れていて判定できない）の 3 値で、判定できないものを合格に混ぜません。

使う・使わないは選べます（既定は無効）

  • ③の「物理的に止める」は、プロジェクトに .claude/phase-gate という空ファイルを置いたときだけ効きます（touch .claude/phase-gate）
  • 個人 PWA や 1 枚の HTML ツールなど、工程分割のコストが見合わない案件では置かないでください
  • 一時的に無効にする環境変数はありません。止めたいときは .claude/phase-gate を消します。消したことが git の差分に残るので、後から「いつ誰が外したか」が分かります
  • 承認記録そのもの（approvals/ の中）への書き込みは、いつでも許可されます。承認者の手が止まっては意味がないためです

Claude には Opus（賢いが高い）と Sonnet（速くて安い）などのモデルがあり、Pro プランでは使える量に上限があります。このキットはSonnet を基本にしても快適に回るように作り直してあります。押さえるのは 4 つです。

  1. 毎回読む量が少ない：共通の約束事 ＋ 規律 3 本だけ読めば始められるよう圧縮してあります（文字数で見て従来の半分）。Claude Code で /context と打つと、いま何が読み込まれているか確認できます
  2. 基本は Sonnet、Opus に上げるのは 3 つの場面だけ：①複数の部品にまたがる設計判断 ②何段も推理が要る不具合の切り分け ③Sonnet に 2 回やらせても収束しない。上げる前に「Opus に何を判断させるか」を 1 行書き、終わったら戻します（/model）
  3. 定型作業は「考える深さ」を下げる：文書の整形、調査結果の要約、決まった手順の繰り返しは /effort で下げると安く速くなります
  4. 上限に当たったら：「セッション上限」「週次上限」は全モデル共通なので、モデルを変えても回復しません。待つか、要約して再開します。「Opus の上限」「Sonnet の上限」と出たときだけ /model で別のモデルに切り替えて続けられます。まず /usage で何に使ったか内訳を見てください
合言葉：「書かせず、読ませる」

デザインの CSS、工程文書、テスト文書は完成品のファイルとして同梱してあります。Sonnet に「同じものを書いて」ではなく「このファイルを読み込んで使って」と言う形にすると、ブレず、安く済みます。

Codex には /model /effort /usage がありません。モデルは設定画面で選び、「話題が変わったら新しい会話にする」だけ守ってください。

測テストの進みと品質を数字で見る

外部結合テストから受け入れテストまでを担当していると、聞かれるのはいつも同じです。「どこまで進んだ？」「あと何日？」「危ない不具合は残ってる？」
今までは工程文書の表を目で数えて答えていました。数えた瞬間から数字は古くなり、数え間違いも起きます。表を埋めるだけで、機械が数えるようにしました。

何を埋めれば、何が出るか

埋めるもの（工程文書の表）出てくる数字・検知
テスト表の 結果（pass / fail / blocked / skip / 未実施。受け入れは 合 / 否 でも可）消化率（実行 ÷ 全件）・合格率（PASS ÷ 実行）。レベル別と全体
テスト表の 実施日 実施者実施ペースと完了予定日（推定。根拠つき）、担当の偏り

実際の出力（図書館貸出の事例）

システムテスト 8 件・受け入れ 5 件・欠陥 3 件を入れて回したときの、そのままの出力です。

./scripts/test-metrics.sh

「判定できない」を合格に数えない

結果欄に「たぶん大丈夫」のような決まった言葉以外が入っていると、その行は「判定できない」として分母に残ります（消した方が消化率は上がりますが、それは水増しです）。1 件でも残っていると、完了判定は「進めない」ではなく「判定できない」になります。
欠陥表そのものが無いときも「0 件」とは言いません。「算出できない」と出ます。

完了してよいか（--gate）

基準は docs/test/TESTING_STRATEGY.md §7 の表に、しきい値と出典つきで書きます。案件ごとに値を変えてよく、出典が空の行は基準として読みません。

./scripts/test-metrics.sh --gate
--- 完了基準（docs/test/TESTING_STRATEGY.md §7）---
  ✗ 1. 消化率（実行済み ÷ 全件。判定できない行も分母に数える）: progress >= 100（実測 58.82）
  ✗ 2. 合格率（PASS ÷ 実行済み）: pass_rate >= 95（実測 80.00）
  ✗ 3. Critical / High の未解決: severe_open == 0（実測 2）
  ✗ 4. 判定できない行（結果欄が語彙外・欠陥表なし）: unread == 0（実測 1）
  手動 5. L3（UI 変更時）全 PASS ＋ スクショ目視、L4（新機能時）依頼者の承認、quality_harness.py PASS
判定候補: **判定できない**（結果欄が語彙外の行が 1 件（語彙に直すか 未実施 にする）。判定不能を合格に数えない）

終了コードは 0（進める）／1（進めない）／2（判定できない）の 3 つ。GO / NO-GO は人が決めます。機械が出すのは「判定候補」と根拠までです。

節トークンを減らす仕組み（何が自動で効いているか）

Pro プランで困るのは「気づいたら上限」です。節約の約束事は前からありましたが、AI が自分で読んで自分で守る前提の散文でした。人が覚えていないと効かない /clear や effort も同じです。
そこで、機械にできるものは全部 hook（見張り役）と設定に落としました。あなたが何もしなくても効きます。

自動で効いているもの

仕組み何をするか全部が要るとき
filter-output.pyテスト・install・build の出力を、Claude が読む前に失敗行と集計だけに絞る。git log は最新 20 件、git diff は --stat に。終了コードは元のままコマンドの先頭に FULL_OUTPUT=1
pre-read-guard.pyロックファイル・minified・node_modules・生成レポートは読ませない（grep で該当行だけ）。800 行超のファイルを丸ごと読もうとしたら先頭 300 行にoffset / limit を指定して読む
context-guard.py55 分以上空けて再開したとき（キャッシュが切れて全履歴を再処理する）と、会話が 4 MB を超えたときに「/clear か要約から」「/compact」を思い出させる。止めはしない—
pre-compact.py圧縮のとき「決定事項・変更ファイル・未解決・テスト集計は残す／ツール出力の本文は捨てる」を指示—
設定 3 つeffortLevel=high（考える深さを 1 段下げる）／autoCompactWindow=200k（Sonnet 5 の 1M を放置しない）／bashOutputMaxChars=12000（超過分はファイルへ退避）設計判断のときだけ /effort xhigh、終わったら戻す
黙って削らない

絞ったときは必ず Claude に「絞った・全部を取る方法」が伝わります。黙って欠けると AI が探し直して逆に高くつくためです。実際にはこう見えます。

テスト出力を失敗行の前後と末尾 5 行に絞りました（filter-output.py）。全量が要るとき: FULL_OUTPUT=1 GATES_REQUESTED=1 pytest tests/
big.py は 900 行あるため先頭 300 行だけ読みました（pre-read-guard.py）。続きは offset=301 を指定する。全部が要ることは稀なので、先に `grep -n` で当たりを付けてから範囲指定で読むのが安い。
[context-guard] 前回の応答から 70 分空いています。プロンプトキャッシュ（寿命 1 時間）が切れ、この 1 通は会話全体を再処理します。無関係な作業なら `/clear` してから送り直す、続きなら「ここまでの決定事項と変更ファイル」を 5 行で要約してから進める

偽のテストで測った実例：102 行の出力が 7 行になり、exit 1（失敗）はそのまま伝わりました。

自分で押すもの（ここだけは人の判断）

  • /clear — 無関係な作業に移るとき。古い会話は 1 通ごとに全部読み直されます
  • /compact — 長い作業の区切りで。何を残すかは pre-compact.py が指示します
  • /effort xhigh — 複数の部品にまたがる設計判断のときだけ。終わったら /effort high
  • Agent の並列委譲は使わない（約 7 倍）。3 役レビューも順番に回します
